# Архитектура и модель данных

## 1. Архитектурный принцип

Новый блок строится как **финансовый домен внутри текущего монолита**, а не как отдельный сервис или второй расчётный контур.

Слои:

1. **Канонические источники** — существующие таблицы и JSON-структуры договоров, расчётов, этапов, заказов, партий и запчастей.
2. **Адаптеры источников** — преобразуют каждую строку в обязательство со стабильным ключом, не меняя смысл источника.
3. **Финансовая проекция обязательств** — единый читаемый реестр, не являющийся третьим независимым графиком.
4. **Факт** — счета, остатки, банковские операции, разнесения, события признания и конвертации.
5. **Детерминированные сервисы** — задолженность, ликвидность, экономика, сверка, объяснения и экспорт.
6. **API и compatibility adapters** — новый `/api/finance`, старая сводка, рабочее место, старые формы факта.
7. **React UI** — новый раздел и ссылки из существующих карточек.

Не добавлять Kafka, отдельный микросервис, второй API-клиент, новый фронтенд-стек или внешний scheduler без необходимости. Использовать текущую SQLAlchemy Session, транзакции FastAPI и существующие фоновые механизмы.

## 2. Канонические источники и приоритеты

| Слой | Источник | Что определяет |
|---|---|---|
| Утверждённый план | Неизменяемая версия расчёта сделки | Базовый/пессимистичный/оптимистичный сценарий, исходный прогноз до договора |
| Юридическое обязательство | `Contract.payment_terms`, изменённое действующим доп. соглашением | Сумма, валюта, событие, юридический срок |
| Оперативный прогноз | Связанный `ExecutionStage`, его `refined_on`/`planned_on` и фактические события | Ожидаемая дата, не заменяющая юридический срок |
| Закупка запчастей | `PurchaseOrder.payments` | Строки обязательств поставщику |
| Логистика | `Batch.payments` | Строки платежей перевозчику/брокеру |
| Ожидание по запчастям | `PartRequest` и расчёт строк | Сумма ожидаемого поступления; без даты не входит в датированную кривую |
| Неустойка | Юридический сервис `obligations()` и решения по неустойкам | Признанная/предъявленная сумма и статус; начисление само по себе не является денежным планом |
| Движение денег | Проведённая `FinanceTransaction` | Подтверждённый банковский факт |
| Выручка/расход | Проведённое `FinanceRecognitionEvent` | Факт признания по документу или хозяйственному событию |

После подписания договора соответствующие прогнозные строки расчёта деактивируются со ссылкой `superseded_by` на договорные обязательства. Одновременное включение обеих строк в итог — ошибка двойного учёта.

## 3. Рекомендуемая структура backend

Имена файлов можно адаптировать к актуальной структуре репозитория, но ответственность сохранить:

```text
backend/app/
  models/finance.py                 # если models разделяется; иначе секция в текущем models
  services/finance/
    money.py                       # Decimal, валюты, округление
    obligations.py                 # проекция, статусы, остатки
    sources/
      calculations.py
      contracts.py
      execution.py
      purchase_orders.py
      batches.py
      parts.py
      penalties.py
    transactions.py                # операции, проведение, сторно
    allocations.py                 # разнесение
    accounts.py                    # счета и остатки
    liquidity.py                   # прогноз и кассовый разрыв
    recognition.py                 # выручка/расход
    economy.py                     # адаптер существующего расчёта и план/факта
    reconciliation.py              # расхождения и миграционная сверка
    questions.py                   # уточнения и scoped доступ
    explanations.py                # трассировка показателей
    exports.py                     # авторизованный XLSX
  api/finance.py                   # тонкий роутер, DTO, Depends
```

Не переносить бизнес-логику в роутер или React. Старые `summary.py`, `workplace.py`, `execution.py`, `legal_contracts.py` и `tasks_files_planfact.py` вызывают общие сервисы, а не копируют запросы и формулы.

## 4. Логическая модель данных

Ниже — обязательный смысл полей и ограничений. Названия можно привести к соглашениям проекта. Все новые таблицы содержат UUID primary key, `created_at`, `updated_at` там, где запись изменяется, `created_by` для пользовательских действий и индексы по основным фильтрам.

### 4.1 `FinanceAccount` — финансовый счёт

Назначение: остатки и движения по счёту компании группы без дублирования банковских реквизитов.

Поля:

- `legal_entity_id` → существующий `LegalEntity`, обязателен;
- `bank_profile_id` → существующий `BankProfile`, обязателен для банковского счёта;
- `title` — рабочее название;
- `currency` — ISO 4217, должна соответствовать валюте банковского профиля;
- `status`: `active | archived`;
- `opened_on`, `archived_on`;
- `note`.

Ограничения и проверки:

- выбранный `BankProfile` должен принадлежать `LegalProfile` с `owner_kind="own"` и `owner_id=legal_entity_id`;
- не создавать копию номера счёта, SWIFT, БИК и банка в `FinanceAccount`;
- один активный финансовый счёт не должен дублировать тот же `bank_profile_id`;
- архивация не удаляет операции и остатки.

### 4.2 `FinanceBalanceSnapshot` — подтверждённый остаток

- `account_id`;
- `as_of` — timezone-aware datetime момента, на который подтверждён остаток;
- `amount: Numeric(18,2)`;
- `source`: `manual | statement_import | migration`;
- `external_ref` — файл/выписка/документ;
- `attachment_id` при наличии;
- `confirmed_by`, `confirmed_at`;
- `note`;
- `reversed_by_snapshot_id` или эквивалентный механизм корректировки без затирания истории.

Последний подтверждённый снимок не перезаписывается молча. Для исправления создаётся новый снимок с объяснением и аудитом.

### 4.3 `FinanceObligation` — проекция строки обязательства

Это не самостоятельный редактор графика. Запись обновляется адаптером источника.

Поля идентичности:

- `source_type`: `calculation | contract | purchase_order | batch | part_request | penalty | …`;
- `source_id` — ID версии расчёта, договора, заказа, партии и т. п.;
- `source_line_key` — стабильный ключ строки;
- `source_revision` — версия/hash исходной строки;
- `source_url` формируется сервисом, а не доверяется клиенту;
- уникальный constraint `(source_type, source_id, source_line_key)`.

Связи:

- `deal_id` nullable;
- `contract_id`, `position_id`, `batch_id`, `purchase_order_id` nullable по типу;
- `legal_entity_id` nullable до уточнения;
- `counterparty_kind`, `counterparty_id`, `counterparty_name_snapshot`;
- `superseded_by_id` nullable self-FK.

Финансовые и временные поля:

- `direction`: `in | out`;
- `nature`: `forecast | contractual | operational | penalty`;
- `title`, `event_code`, `source_line_no`;
- `amount: Numeric(18,2)`;
- `currency: String(3)`;
- `legal_due_on` nullable;
- `legal_due_text` — если срок зависит от ещё не наступившего события;
- `event_on` nullable;
- `event_is_fact: Boolean`;
- `forecast_on` nullable;
- `basis_snapshot: JSON` — минимальный проверяемый снимок исходных полей, без секретов;
- `is_active`;
- `excluded_reason` nullable;
- `sync_status`: `ok | conflict | orphaned`;
- `synced_at`.

Не хранить `paid_amount` и `status` как независимо редактируемые поля. Они вычисляются по подтверждённым разнесениям и дате «на».

Правила:

- отсутствие строки в источнике при повторной синхронизации переводит её в `orphaned`/неактивное состояние, а не удаляет, если есть разнесения или история;
- при изменении суммы/валюты строки с существующими разнесениями автоматическое перезаписывание запрещено: `sync_status=conflict`, создаётся сверка;
- `forecast_on` не редактируется как третий график. Оно выводится из связанного этапа либо из даты источника;
- `legal_due_on` не заменяется уточнённой датой этапа;
- для суммы без даты `forecast_on=NULL`, а не `date.today()`.

### 4.4 Стабильные ключи строк

Для новых/черновых графиков рекомендуется добавлять `line_uid` внутрь исходной JSON-строки до подписания/проведения. Для существующих подписанных договоров **не переписывать JSON ради миграции**.

Ключи:

- расчёт: `client:{variant_id}:{line_uid|no}` и `factory:{position_id}:{line_uid|no}` с `source_id=approved_deal_version_id`;
- договор: `payment:{line_uid|legacy_no}`;
- заказ поставщику: `payment:{line_uid|index}`;
- партия: `payment:{line_uid|index}`;
- этап исполнения: связь через отдельное поле `ExecutionStage.finance_obligation_id`, а не через совпадение суммы;
- неустойка: стабильный `key` юридического сервиса.

`source_revision` вычисляется из канонически сериализованных значимых полей. Изменение порядка строк не должно молча переносить старые банковские разнесения на другую строку. При неоднозначном matching создаётся ручная сверка.

### 4.5 `FinanceTransaction` — банковская операция или заявление о платеже

- `account_id` nullable только для непроведённой/требующей сверки записи;
- `direction`: `in | out`;
- `amount: Numeric(18,2)`, положительная; знак определяется направлением;
- `currency`;
- `booked_at` — дата/время банковского движения;
- `value_date` nullable;
- `counterparty_name`, `purpose` — без неразрешённого раскрытия в задачах;
- `external_ref` — банковский идентификатор;
- `import_batch_id` nullable;
- `status`: `draft | needs_reconciliation | posted | reversed`;
- `reversal_of_id` nullable self-FK;
- `reversed_by_id` nullable;
- `origin_type`: `manual | bank_import | execution_legacy | contract_legacy | planfact_legacy | migration | fx | reversal`;
- `origin_id` nullable;
- `idempotency_key`, уникальный;
- `note`, `created_by`, `posted_by`, `posted_at`.

Инварианты:

- `posted` требует существующий активный счёт, валюту операции, совпадающую со счётом, дату и положительную сумму;
- для `posted` уникален `(account_id, external_ref)` при непустом `external_ref`;
- ручная отметка старого UI создаёт `needs_reconciliation`, не `posted`;
- нельзя создать фиктивный системный счёт, чтобы формально провести старый факт;
- проведённая операция не удаляется и её финансовые поля не меняются обычным PUT. Ошибка исправляется reversal + новая операция;
- повтор запроса с тем же idempotency key возвращает существующий результат, а не новую запись.

Дополнительно рекомендуется `FinanceTransactionSource` с `(transaction_id, source_type, source_id)` и уникальным `(source_type, source_id)`. Она позволяет связать несколько старых представлений одного платежа без повторного финансового эффекта.

### 4.6 `FinanceAllocation` — разнесение операции на обязательство

- `transaction_id`;
- `obligation_id`;
- `amount_tx: Numeric(18,2)` — сумма в валюте операции;
- `amount_obligation: Numeric(18,2)` — сумма погашения в валюте обязательства;
- `fx_rate: Numeric(18,8)` nullable — обязателен при разных валютах, с `fx_source` и `fx_on`;
- `status`: `provisional | confirmed | reversed`;
- `allocated_on`;
- `idempotency_key`;
- `created_by`, `confirmed_by`, `confirmed_at`;
- `reversal_of_id` nullable;
- `note`.

Инварианты:

- суммы положительные;
- направление операции и обязательства согласованы;
- `confirmed` допускается только для `posted` операции;
- сумма активных разнесений операции не превышает её сумму;
- сумма подтверждённых погашений обязательства не превышает сумму обязательства без отдельного контролируемого сценария переплаты;
- переплата остаётся неразнесённой либо оформляется отдельным обоснованным объектом, а не молча увеличивает обязательство;
- одна операция может закрывать много обязательств, одно обязательство — много операций;
- сторнирование операции сторнирует/деактивирует связанные разнесения атомарно.

### 4.7 `FinanceRecognitionEvent` — признание выручки/расхода

- `kind`: `revenue | expense`;
- `deal_id` nullable;
- `obligation_id` nullable — связь не означает равенство оплаты и признания;
- `cost_item_code` nullable, обязателен для расхода по статье сделки;
- `position_id` nullable;
- `amount`, `currency`, `fx_rate`, `fx_source`, `fx_on`;
- `recognized_on`;
- `basis_type`: `primary_document | business_event | legacy_business_event`;
- `document_type`, `document_number`, `document_date` nullable только если реально отсутствуют;
- `attachment_id` nullable;
- `source_type`, `source_id`, уникальная пара для адаптера;
- `status`: `posted | reversed`;
- `reversal_of_id`, `idempotency_key`, `comment`, `created_by`.

Новое событие требует понятного основания. Для legacy-записи нельзя выдумывать номер документа: используется `legacy_business_event`, запись помечается для сверки.

Поступление/списание денег само по себе не создаёт `RecognitionEvent`.

### 4.8 `FinanceFxOperation` — конвертация

- `sell_transaction_id`, `buy_transaction_id` — две разные проведённые операции;
- `sell_account_id`, `buy_account_id` денормализуются только для контроля;
- `sell_amount`, `sell_currency`, `buy_amount`, `buy_currency`;
- `rate: Numeric(18,8)`, `rate_source`, `executed_at`;
- `external_ref`, `idempotency_key`, `comment`.

Инварианты: счета и валюты соответствуют ногам, суммы согласованы с операциями, одна нога не используется в двух независимых конвертациях. Внутригрупповое перемещение и конвертация не создают выручку/расход.

### 4.9 `FinanceImportBatch` — пакет импорта

- `account_id`, `file_name`, `file_sha256`, `mapping`, `rows_total`, `rows_valid`, `rows_duplicates`, `rows_errors`;
- `status`: `preview | confirmed | cancelled`;
- `idempotency_key`, `created_by`, `confirmed_at`;
- ошибки строк в отдельном JSON/child table без секретов.

Preview ничего не проводит. Повторное подтверждение того же файла не создаёт дубли.

### 4.10 `FinanceQuestion` — уточнение

- `subject_type`: `obligation | transaction | recognition | account | deal_metric | reconciliation`;
- `subject_id`;
- `deal_id` nullable;
- `question`, `context_snapshot` — минимальный серверно сформированный разрешённый контекст;
- `asked_by`, `assignee_id`, `due_on`;
- `status`: `open | answered | verified | rejected | closed`;
- `answer`, `answered_at`;
- `reviewed_by`, `reviewed_at`, `review_comment`;
- `source_updated_by`, `source_updated_at`, `source_update_ref`;
- `attachment_ids`/связь с существующими файлами;
- `created_at`, `updated_at`.

Не дублировать вопрос второй записью `Task`. Включать открытые `FinanceQuestion` в существующий ответ `/api/tasks/my` как task-like элементы с `kind="finance_question"`, отдельным URL и обработчиком завершения. Для уведомлений использовать существующий `NotificationLog`/адаптер. Это позволяет поддерживать вопросы и по объектам без сделки, не меняя NOT NULL `Task.deal_id` и не создавая фиктивные сделки.

## 5. Дополнительные поля существующих моделей

Предпочтительно аддитивно добавить:

- `ExecutionStage.finance_obligation_id` nullable FK;
- `ExecutionStage.source_line_key` nullable, если требуется восстановление связи;
- при необходимости `PlanFactEntry.finance_transaction_id` и `finance_recognition_event_id` nullable;
- служебные `line_uid` только в новых/черновых исходных JSON-строках, без перезаписи подписанных документов.

Не менять типы существующих денежных `Float` массово в этом внедрении. Новые таблицы используют точные типы; на границе старого кода выполняется `Decimal(str(value))`.

## 6. Проекция и синхронизация

### Запуск

- при изменении источника — соответствующий сервис вызывает адаптер в той же транзакции;
- для чтения старого источника без события — контролируемый `sync_source` перед построением отчёта, без скрытых записей при каждом GET, если это создаёт гонки;
- для всей базы — явная команда `finance rebuild --dry-run` и затем подтверждённый запуск;
- периодическая сверка использует текущий фоновый механизм, но не создаёт неподтверждённый банковский факт.

GET финансового реестра не должен без необходимости мутировать всю БД. Первичную миграцию и полную пересборку выполняет отдельная команда с отчётом.

### Идемпотентность

Один источник → один `FinanceObligation` по уникальному ключу. Повторная сборка с тем же `source_revision` ничего не меняет. При новом hash обновляются только разрешённые поля проекции и пишется аудит.

### Замещение плана договором

1. Адаптер находит активные forecast-строки утверждённой версии для той же сделки/стороны.
2. Связывает их с договорными строками по явным ссылкам, а при legacy — по набору признаков: сделка, вариант/позиция, направление, событие, сумма/доля, валюта, порядок.
3. Однозначное соответствие: forecast `is_active=false`, `superseded_by=contract_obligation`.
4. Неоднозначное соответствие: не объединять молча; сформировать `reconciliation` и исключить доказанный дубль из итогов только по утверждённому правилу.
5. До разрешения показывать предупреждение и консервативно исключать заведомый forecast-дубль из общей кривой с трассировкой причины. Не удалять данные.

## 7. Расчёт статусов и задолженности

Для обязательства `o` на дату `as_of`:

```text
confirmed_paid(o) = Σ active confirmed FinanceAllocation.amount_obligation
provisional_paid(o) = Σ active provisional FinanceAllocation.amount_obligation
remaining(o) = max(o.amount − confirmed_paid(o), 0)
```

Округление — до точности валюты на представлении, внутренние проверки используют Decimal.

- `paid`: `remaining = 0` и `amount > 0`;
- `partially_paid`: `0 < confirmed_paid < amount`;
- `overdue`: `remaining > 0`, `legal_due_on < as_of`;
- `needs_reconciliation`: дополнительный независимый флаг при provisional/legacy/conflict;
- `no_date`: `remaining > 0`, отсутствуют и юридический срок, и прогноз;
- `superseded`: не входит в активные итоги.

Просрочка считается от юридического срока, если он определён. Если обязательство зависит от будущего события, юридический срок не выдумывается; используется текст условия и прогноз. Оперативный перенос не стирает просрочку по договору.

## 8. Остатки и ликвидность

### Подтверждённый остаток счёта на момент T

```text
balance(account, T) =
  последний подтверждённый FinanceBalanceSnapshot с as_of ≤ T
  + Σ posted inflow после снимка и ≤ T
  − Σ posted outflow после снимка и ≤ T
  − Σ сторнирующих корректировок по единым правилам
```

Если снимка нет, остаток `unknown`, а не ноль. UI и API обязаны отличать неизвестный остаток от нулевого.

### Прогноз

Для каждой валюты и счёта/группы счетов:

```text
projected_balance(day) =
  confirmed_opening_balance
  + posted movements up to day
  + active forecast inflows with forecast_on = day
  − active forecast outflows with forecast_on = day
  ± scheduled FX legs
```

- проведённые операции не повторяются как прогнозные обязательства: обязательство уменьшается на подтверждённое разнесение;
- `needs_reconciliation` не включается в подтверждённый остаток;
- суммы без даты выводятся отдельно;
- кассовый разрыв — период, когда прогнозный остаток ниже заданного минимума; минимум по умолчанию 0, но порог может быть настройкой;
- для RUB-консолидации каждая сумма переводится по явно указанному курсу на дату отчёта/прогноза. Нельзя использовать неявно текущий курс для прошлого факта;
- отчёт хранит/возвращает набор курсов и их источники для воспроизводимости.

### Фактический кассовый разрыв сделки

Строится по подтверждённым операциям, разнесённым на обязательства сделки, с хронологией фактических поступлений/списаний. Если сделка имеет операции без разнесения, они показываются отдельно и не приписываются ей автоматически. Если начальный остаток не нужен для сделочной кривой, она начинается с нулевого **сальдо самой сделки**, но это не подменяет кривую ликвидности компании, которая начинается с фактического остатка.

## 9. Экономика и план/факт

Существующий расчётный движок остаётся источником плановых сценариев. Новый сервис собирает:

```text
План       = утверждённая DealVersion + base/pess/optimistic
Прогноз    = активные договоры + оперативные этапы + актуальные курсы/уточнения
Факт P&L   = posted FinanceRecognitionEvent
Факт cash  = posted FinanceTransaction + confirmed FinanceAllocation
```

Правила миграции старого план/факта:

- `cost_item` → одно legacy recognition event по `source_id=PlanFactEntry.id`; повторный запуск не дублирует;
- `payment_in/payment_out` → только платёжная сторона, никогда не revenue/expense;
- `PlanFactEntry.ref="stage:{id}"` связывается с тем же legacy payment claim, что и этап, а не создаёт вторую операцию;
- `delivery` остаётся фактом срока, не создаёт выручку автоматически;
- `fx` в старом `FactIn` — фактическое значение курса для отчёта, а не двухногая конвертация; в остатки оно не включается;
- закрытый план/факт не переписывается молча. Изменения допускаются по существующим правам ФД с аудитом.

## 10. Переходный период старых платёжных отметок

Старые `Contract.facts.pay`, `ExecutionStage.actual_*` и связанные `PlanFactEntry` могут описывать один платёж. Миграция выполняется в три шага:

1. инвентаризация и dry-run с количеством совпадений, конфликтов и кандидатов на дубли;
2. создание записей `needs_reconciliation` и provisional allocations только по однозначным связям;
3. ручное подтверждение ФД: выбор реального счёта, банковской операции, суммы и связей; после этого запись становится `posted`, разнесение — `confirmed`.

Старые поля не удаляются в этом этапе. После включения нового контура:

- этап платежа получает факт из финансового сервиса;
- старый endpoint может сохранять legacy-отметку как `needs_reconciliation` для совместимости, но ответ явно содержит предупреждение и статус;
- старый UI получает ссылку «Подтвердить в Финансах»;
- никакой автоматический адаптер не ставит `posted` без счёта и банковского подтверждения.

## 11. Транзакции, блокировки и аудит

- операции `post`, `allocate`, `reverse`, `confirm import`, `verify question` выполняются атомарно;
- при разнесении блокируются операция и обязательства (`SELECT … FOR UPDATE` в PostgreSQL) либо используется эквивалентная защита от гонки;
- уникальные constraints — обязательная последняя линия защиты, приложение их не заменяет;
- ошибка constraint возвращает понятный 409, а не 500;
- каждый mutation пишет существующий `AuditLog`: actor, object, before/after, reason, source, idempotency key;
- финансовые суммы не попадают в общие уведомления пользователям без права;
- фоновые повторы безопасны благодаря уникальным ключам.

## 12. Объяснимость

Каждый агрегат строится функцией, возвращающей одновременно `value` и `trace`:

```json
{
  "value": "…",
  "as_of": "…",
  "filters": {},
  "formula": "…",
  "included": [{"id": "…", "source": "…", "amount": "…", "currency": "…"}],
  "excluded": [{"id": "…", "reason": "…"}],
  "fx": [{"currency": "CNY", "rate": "…", "on": "…", "source": "…"}],
  "source_revisions": {}
}
```

`trace` подвергается тем же правам, что и показатель. Нельзя через explanation получить скрытые строки себестоимости или закупки.

## 13. Миграции схемы

В базовой выгрузке реальная Alembic-конфигурация отсутствует; `init_db()` создаёт таблицы/столбцы для dev, а комментарий ссылается на `alembic upgrade head` в production. Поэтому:

- не утверждать, что production-миграции уже работают;
- для dev добавить новые таблицы через существующий `create_all` и только аддитивные столбцы;
- для production подготовить настоящую reviewed Alembic migration в существующем контуре, если он появился в актуальном репозитории; если контура по-прежнему нет, подготовить и явно отметить необходимый migration script/change set как блокер production rollout;
- не запускать автоматически на рабочей БД;
- перед rollout: backup, dry-run, сверка counts/sums, план rollback без удаления финансовой истории;
- никаких destructive rename/drop и неявных UPDATE утверждённых расчётов/подписанных условий.

## 14. Индексы и производительность

Минимум:

- обязательства: `(deal_id, forecast_on)`, `(legal_due_on)`, `(source_type, source_id, source_line_key)`, `(legal_entity_id, direction)`, `(is_active)`;
- операции: `(account_id, booked_at)`, `(external_ref)`, `(status)`, `(idempotency_key)`;
- разнесения: `(obligation_id, status)`, `(transaction_id, status)`;
- признания: `(deal_id, kind, recognized_on)`, `(cost_item_code)`;
- вопросы: `(assignee_id, status, due_on)`, `(subject_type, subject_id)`.

Списки используют пагинацию и агрегирование на уровне БД. Не загружать все операции и договоры в Python ради каждого KPI. Проверить отсутствие N+1 на совместных запросах.
