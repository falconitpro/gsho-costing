# Протокол продолжения работы и правок в том же диалоге

## 1. Цель

Последующее сообщение пользователя может менять одну формулировку, экран, правило расчёта или интеграцию. Оно не должно приводить к новому проекту, откату готовых этапов или потере уже принятых решений.

Исходный ZIP остаётся базовой точкой. Рабочая актуальная версия документов находится в `docs/finance/` репозитория. Именно её Claude читает и обновляет после начала внедрения.

## 2. Приоритет источников при правке

1. Новое явное сообщение пользователя в текущем диалоге.
2. Новые решения в журнале, помеченные как заменяющие прежние.
3. Ранее принятые решения, не отменённые пользователем.
4. Актуальный код — для фактического состояния реализации, но не для молчаливой отмены продукта.
5. Базовая выгрузка 08.11.2026 — только исторический ориентир.

Если пользователь явно меняет решение, не спорить и не сохранять старое поведение ради исходного архива. Зафиксировать замену и привести зависимые места в соответствие.

## 3. Обязательное начало каждой правки

Перед изменением кода:

1. Прочитать новое сообщение целиком и выделить конкретный ожидаемый результат.
2. Прочитать `09_Журнал_решений.md`, `10_Состояние_внедрения.md` и последний отчёт этапа.
3. Проверить `git status`, текущий diff, ветку/commit и незавершённые миграции.
4. Найти все затронутые места поиском по коду, а не только файл, который первым пришёл в голову.
5. Определить, является ли правка новой или уже реализованной в другом месте.
6. Записать короткий impact analysis: решение → код → API → UI → права → миграция → тесты → документация.

Не начинать с массового rewrite. Не создавать новый параллельный компонент только потому, что существующий уже большой.

## 4. Классификация правки

### A. Текст/визуал

Проверить design tokens, адаптивность, loading/error/empty и скриншоты. Не менять финансовую логику.

### B. Финансовое правило

Найти канонический сервис, все compatibility adapters, explanation, export и тесты. Не исправлять только один экран, если та же формула используется Workplace/Summary.

### C. Интеграция

Проверить источник, projection key, замещение дублей, объектные права, обратные ссылки, миграционную сверку и старые endpoint.

### D. Права

Проверить чтение, mutation, nested DTO, trace, export, files, tasks, notifications и scoped question. Изменение кнопки недостаточно.

### E. Модель данных/миграция

Сохранить существующие данные и идемпотентность. Подготовить upgrade на пустой и базовой БД, dry-run, counts/sums и rollback приложения. Не использовать destructive упрощение.

### F. Отмена ранее принятого решения

Добавить новое решение со статусом `ПРИНЯТО`, полем `supersedes` и причиной. Прежнее перевести в `ЗАМЕНЕНО`, не удаляя историю. Обновить все зависимые документы и код.

## 5. Минимальный безопасный diff

Разрешено менять:

- файлы, непосредственно реализующие правку;
- зависимые adapters/services/tests;
- затронутые спецификации и журнал состояния;
- миграции, если структура действительно затронута.

Запрещено без отдельной необходимости:

- форматировать весь репозиторий;
- обновлять все зависимости;
- менять глобальные стили;
- переписывать несвязанные модули;
- удалять «лишний» старый код, если он обслуживает compatibility;
- откатывать изменения более новых PR;
- пересоздавать уже принятые модели и маршруты под другим именем;
- менять страницу входа или другие разделы CRM.

## 6. Порядок реализации правки

1. Зафиксировать текущее состояние и, при необходимости, failing regression test.
2. Добавить/обновить решение в журнале.
3. Изменить канонический источник/сервис.
4. Обновить зависимые API и compatibility adapters.
5. Обновить UI и ссылки.
6. Обновить права и экспорт, если затронуты.
7. Обновить миграции и dry-run, если затронуты.
8. Обновить спецификации только в затронутых разделах.
9. Запустить профильные и регрессионные проверки.
10. Обновить состояние, список файлов и отчёт.

Если правка небольшая, не раздувать её в новый этап. Если она меняет фундамент — остановиться на безопасной границе и явно обозначить масштаб до destructive/необратимых действий.

## 7. Обязательные проверки после правки

Минимум:

- новый/обновлённый тест, воспроизводящий запрос;
- тесты всех затронутых модулей;
- регрессия Summary/Workplace/Legal/Execution/PlanFact по карте зависимостей;
- frontend typecheck/build при изменении frontend;
- реальный браузерный сценарий при изменении UI;
- повторная миграция/сверка при изменении источника или схемы;
- проверка прав, если менялись поля или endpoints.

Нельзя ограничиться фразой «проверил визуально». Указать фактические команды, сценарии и результат.

## 8. Работа с ошибками и уточнениями

- Если ошибка возникла из-за правки — исправить первопричину, а не скрыть тест/удалить assert.
- Если ошибка была в baseline — зафиксировать отдельно и не выдавать за новую регрессию.
- Если данных недостаточно для однозначного выбора, задавать только конкретный блокирующий вопрос. Не спрашивать повторно то, что уже решено пакетом.
- Если можно продолжить безопасную часть, продолжить её и оставить узкий блокер в состоянии.
- Не выдумывать банковские курсы, счета, суммы, статусы или production migration path.

## 9. Если диалог был сжат или прерван

Восстановление выполняется по артефактам, а не по памяти:

1. прочитать актуальные `09`, `10`, последний `11`-отчёт;
2. изучить commit/diff;
3. сопоставить чек-лист этапа с фактическими файлами и тестами;
4. не повторять уже завершённые миграции;
5. не создавать вторую версию модуля;
6. продолжить с первого незавершённого проверяемого действия.

Если репозиторий недоступен, честно указать, что последнее подтверждённое состояние находится в журнале, но фактический код не проверен.

## 10. Формат ответа после правки

Отвечать кратко и по результату:

1. **Изменено:** конкретное поведение и файлы/области.
2. **Не затронуто:** важные соседние функции, которые остались без изменений.
3. **Проверено:** фактические тесты, браузерные сценарии, скриншоты при UI.
4. **Решения:** ID новой/изменённой записи журнала.
5. **Осталось:** только реальные ограничения/блокеры.
6. **Следующий шаг:** одно конкретное действие, если работа не завершена.

Не пересказывать весь проект и не выдавать новый общий план вместо исполнения.

## 11. Пример правильной записи замены

```markdown
### D-041 — Изменён горизонт «скоро срок»
- Дата: 2026-11-…
- Статус: ПРИНЯТО
- Заменяет: D-0xx
- Основание: сообщение пользователя в текущем диалоге.
- Решение: …
- Затронуто: obligations service, calendar filter, API query, tests FIN-…, UI-спецификация §8.
- Проверено: …
```

Старая запись остаётся с отметкой `ЗАМЕНЕНО D-041`. Благодаря этому следующий запрос продолжает историю, а не начинает сравнение вариантов заново.
