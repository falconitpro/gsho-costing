# Карта интеграции с существующей CRM

## 1. Базовая точка и правило сверки

Карта подготовлена по выгрузке `main` от 08.11.2026, PR до #116. Пути указаны относительно `07_Код/` исходной выгрузки. В приложённом репозитории каталог `07_Код` может отсутствовать — работай с корнем backend/frontend.

Перед реализацией сверь каждую строку карты с актуальным кодом. Если функция переехала, найдите новую и обновите карту в журнале. Не восстанавливайте старую структуру и не откатывайте более новые PR.

## 3. Сделки и утверждённые расчёты

### Что использовать

- утверждённую версию расчёта и выбранный вариант;
- существующие `ScenarioResult`: `items_rub`, `cost_total_rub`, `price_rub`, `margin_pct`, `profit_rub`, `cash_gap`, `cashflow`, `finance_breakdown`, `sensitivity`;
- `payment_dates` и заводские графики позиций для forecast-обязательств;
- существующие права `cost` и `finance_analytics`.

### Что изменить

1. Написать read adapter, который не сериализует заново весь расчёт в произвольном виде, а возвращает стабильный финансовый DTO с `deal_version_id`, сценарием и источником.
2. Forecast-строки до договора создавать с ключом от неизменяемой версии.
3. При новой утверждённой версии не переписывать старую проекцию: прежняя версия остаётся исторической, активный прогноз переключается по правилам сделки с аудитом.
4. После подписания договора замещать соответствующий forecast договорными строками.
5. В экономике сделки различать плановый cash gap расчёта, текущий прогноз и факт по банковским операциям.

### Запреты

- не пересчитывать старую утверждённую версию «улучшенным» алгоритмом;
- не изменять Excel/KP/визы прошлой версии;
- не выдавать менеджеру `calc_result`, статьи, маржу или закупочные условия через новый summary;
- не считать цену клиента фактической выручкой.

### Многосделочный договор

Если используются `Contract.deal_ids`, обязательство появляется в общем реестре **один раз**. Для распределения по экономике нескольких сделок нужна явная связь `obligation_id + deal_id + amount/share` и контроль суммы долей. Без неё показатель доступен на уровне договора/группы, но не размазывается по сделкам автоматически. Дублировать обязательство на каждую сделку запрещено.

## 4. Юридический блок и договоры

### Текущие функции, которые надо переиспользовать

`legal_contracts.schedule(db, c, today)` уже возвращает по строке:

- `no`, `amount`, `currency`, `share_pct`;
- `event`, `event_on`, `event_fact`;
- `due_on`, `due_legal`;
- `days_overdue`.

Адаптер обязан строить юридическую дату именно на этой логике, включая календарные/рабочие дни и зависимость просрочки от факта события. Не писать второй калькулятор сроков.

`obligations()` остаётся источником исполнения, неустоек, решений `claimed/recognized/waived` и лимитов ответственности. Финансовый раздел показывает их через адаптер.

### Проекция платежей

- активный подписанный договор направления `income/expense` → одна `FinanceObligation` на каждую строку `payment_terms`;
- `nature=contractual`;
- `legal_due_on=due_on`, `legal_due_text=due_legal`;
- `event_on/event_is_fact` из schedule;
- `forecast_on` из связанного этапа, а при его отсутствии — из рассчитанного ожидаемого события/срока;
- черновик договора не заменяет утверждённый forecast и не становится юридическим долгом;
- расторгнутый/аннулированный договор исключается по явному правилу с сохранением факта и аудита;
- действующее доп. соглашение обновляет источник и запускает синхронизацию; строки с разнесениями при конфликте идут в сверку.

### Подписанный договор

Сохранить существующие ограничения `LOCKED`, `TERMS_FIELDS`, `LOCKED_OK`, `correction_reason`, доп. соглашения и уведомления. Финансовый API не получает права записи `payment_terms`, `amount`, `currency`, `penalties`, `security` и других юридических условий.

### `Contract.facts`

- `perf` и `pen` продолжают обслуживаться юридическим блоком;
- `pay` становится compatibility-входом финансового адаптера;
- старое `paid_on` не означает автоматически полную оплату: сумма определяется банковскими разнесениями;
- при наличии только старой отметки обязательство получает `needs_reconciliation`;
- юридический ответ сохраняет текущие поля, но дополнительно может содержать `finance_status`, `confirmed_paid`, `remaining` с явной семантикой.

### UI

В карточке договора добавить ссылку:

`/finance?tab=calendar&contract_id={id}`

В карточке финансового обязательства — обратную:

`/legal?tab=contracts&open={contract_id}`

Ссылки показываются только при доступе к целевому объекту; при отсутствии права сервер возвращает корректный 403/404 без утечки данных.

## 5. Этапы исполнения

### Текущая проблема

`execution_service.py` объединяет все авансы клиента в один `client_advance` с минимальной датой и суммой, остальные клиентские платежи — в `client_final` с максимальной датой. Заводские платежи после первого также суммируются с самой поздней датой. Это теряет детализацию и делает частичную оплату неоднозначной.

### Целевая модель

1. Неплатёжные этапы остаются без изменения.
2. Платёжный этап — оперативная проекция **одной** финансовой/договорной строки:
   - сохраняются существующие `code` (`client_advance`, `client_final`, `factory_advance`, `factory_final`) для совместимости;
   - допускается несколько этапов с одним `code`;
   - добавляются `finance_obligation_id` и при необходимости `source_line_key`;
   - `amount/currency` зеркалят источник, не редактируются независимо;
   - `baseline_on` фиксируется по существующим правилам;
   - `planned_on/refined_on` задают оперативный прогноз;
   - юридическая дата остаётся в договоре/обязательстве.
3. В UI группа может визуально сворачиваться, но каждая строка доступна отдельно.
4. Для платёжного этапа `actual_on/actual_amount` выводятся из подтверждённых финансовых разнесений. Несколько частичных платежей видны в карточке обязательства.

### Старые агрегированные этапы

- не разрывать автоматически старый факт между несколькими строками по пропорции;
- сохранить legacy group для сверки, если факт уже внесён и соответствие неоднозначно;
- незаполненные/будущие этапы можно перестроить в детальные после dry-run;
- задачи и старые stage ID не удалять без миграции ссылок;
- `POST /stages/{stage_id}/actual` для детальной строки создаёт legacy `needs_reconciliation` через общий сервис, для неоднозначной legacy group направляет в Finance и не распределяет сумму произвольно.

### События и сроки

Существующая логика пересчёта дат следующих этапов, приёмки и `factory_final` сохраняется. Запрет окончательного расчёта с заводом до приёмки не обходится новым финансовым API: при создании/проведении связанного платежа проверяется действующее бизнес-правило либо платёж явно попадает на сверку согласно принятому процессу. Нельзя молча отменить контроль приёмки.

## 6. План/факт и `PlanFactEntry`

### Compatibility

`FactIn` и старые формы можно сохранить для пользователей, но обработчик становится адаптером:

- `cost_item` → recognition expense + связь с `PlanFactEntry`;
- `payment_in/payment_out` → `FinanceTransaction(needs_reconciliation)` + provisional allocation при однозначном обязательстве;
- `delivery` → существующий факт срока;
- `fx` → курс для план/факта, не конвертация и не банковское движение.

Ответ сохраняет ожидаемые поля и дополнительно сообщает статус сверки. Повтор по `ref`/source key не создаёт дубль.

### Отчёт

- план берётся из утверждённой версии;
- `revenue_fact` — сумма posted recognition revenue;
- `cost_fact` — posted recognition expense по 18 статьям;
- оплаты отображаются в cash-блоке;
- `cash_gap.fact` — из подтверждённых операций сделки;
- отсутствие достаточных данных — `None`/«недостаточно данных» с объяснением, а не постоянный заглушечный `None` при наличии данных;
- закрытие отчёта и редактирование после закрытия подчиняются текущим правам ФД.

### UI

В `PlanFactTab.tsx`:

- сохранить привычный отчёт;
- разделить «Прибыль и признание» и «Деньги»;
- показать статус банковской сверки платёжных записей;
- добавить ссылку `/finance?tab=economy&deal_id={deal.id}`;
- не добавлять второй редактор банковских операций в эту вкладку.

## 7. Старый экран «Деньги» и `/api/summary/money`

### Текущие ограничения

- учитываются только четыре кода этапов;
- фактические этапы исключаются;
- нет полноценных операций, остатков и разнесения;
- кривая начинается с `cum=0`;
- в кривую входят только RUB;
- запчасти показываются отдельно без даты.

### Целевой адаптер

Endpoint остаётся доступным и проверяет `finance_analytics`, но обращается к `finance.liquidity/obligations`.

Сохранить по возможности ключи:

- `rows`, `receivables`, `guarantees`, `curve`, `parts`, `totals`;
- внутри строк сохранить старые поля и добавить новые только аддитивно;
- `curve.cum` теперь означает прогнозный остаток с входящим балансом;
- если входящий баланс неизвестен, возвращать `balance_status="unknown"` и nullable показатели остатка вместо фиктивного нуля;
- `parts` без даты остаётся вне кривой;
- мультивалютные суммы передаются отдельными группами и RUB-эквивалентом;
- `totals.min_cum` не должен притворяться реальным минимумом при неизвестном остатке.

Это осознанное уточнение семантики: описать его в отчёте миграции и обновить тесты, не сохраняя ошибочный нулевой старт ради формальной совместимости.

`/summary?kind=money` либо перенаправляет на `/finance?tab=overview`, либо рендерит wrapper. Предпочтителен redirect с сохранением поддерживаемых query-параметров. Пункт старой сводки не должен показывать два конкурирующих расчёта.

## 8. Рабочее место

`workplace.py` не поддерживает собственную кассовую формулу. Для ФД/ЗГД и других пользователей с `finance_analytics`:

- быстрая ссылка «Финансы» → `/finance`;
- блок money получает укороченный DTO из общего overview service;
- показываются ближайшие поступления/списания, просрочки, минимальный прогнозный остаток и неразнесённые операции;
- при неизвестном остатке — призыв подтвердить остаток, а не нулевой KPI;
- старая ссылка `/summary?kind=money` продолжает работать через compatibility.

Нельзя возвращать финансовый блок пользователю только на основании роли, если действующие overrides запрещают `finance_analytics`.

## 9. Запчасти

### Продажа/заявка клиента

`parts_deals.rows()` возвращает `ordered_rub` для заказанных, но ещё не отгруженных строк. Это ожидаемые поступления, а не датированная дебиторка.

Правила:

- создавать прогнозную строку без даты только если ещё нет соответствующего договора/графика;
- `forecast_on=NULL`, отдельный блок «ожидается, срок не согласован»;
- не использовать `updated_at`, дату отгрузки или сегодняшний день как срок оплаты;
- после появления `Contract` вида `client_parts` связать и заместить прогноз;
- частично отгруженные/отменённые/заменённые строки учитывать по существующему статусу, без двойной суммы;
- переход на `/deals/parts/{id}` сохранить.

### Заказ поставщику

Каждая запись `PurchaseOrder.payments`:

- `due` → дата источника;
- `amount` → сумма;
- `comment` → описание;
- `paid_on` → legacy payment claim, требующий сверки, а не автоматически подтверждённый банковский факт.

При отсутствии валюты в старой строке валюта определяется из заказа/поставщика только по существующему достоверному полю; если её нет, ставится конфликт «валюта не определена», а не молча RUB.

## 10. Логистические партии

Каждая запись `Batch.payments` включается отдельно. Связь: `deal_id`, `batch_id`, строка, направление `out`.

- дата и сумма берутся из источника;
- назначение перевозчик/брокер и валюта проверяются по существующим полям;
- логистические расходы в план/факте связываются с соответствующей статьёй только по явному маппингу;
- оплата логистики не считается автоматически признанным расходом;
- факт отгрузки/границы/ДТ остаётся в существующих полях партии и может влиять на событие срока через каноническую логику.

## 11. Компании группы, профили и банки

Использовать `legal_profiles.ensure_profiles()` и текущие отношения:

```text
LegalEntity → LegalProfile(owner_kind="own", owner_id=LegalEntity.id)
            → BankProfile
            → FinanceAccount
```

Проверки:

- компания и профиль активны;
- банковский профиль действующий;
- валюта совпадает;
- реквизиты не копируются в новые таблицы;
- изменение реквизитов продолжает идти через юридический блок с историей и верификацией;
- `Contract.own_bank_id` может подсказать вероятный счёт для разнесения, но не является доказательством банковского движения;
- при архивировании банковского профиля операции и история финансового счёта сохраняются.

## 12. Задачи, уведомления и вопросы

### Интеграция без изменения `Task.deal_id`

`FinanceQuestion` — основной объект. Открытые вопросы добавляются в результат `/api/tasks/my` общим сервисом наряду с `Task`:

- `kind="finance_question"`;
- `id` вопроса;
- `deal_id` nullable;
- `title`, `due`, `assignee_id`, `overdue`;
- `url=/finance?tab=reconciliation&question={id}` для финансового пользователя;
- для ответственного без права — scoped URL/действие ответа, а не полный реестр.

Не создавать дополнительный `Task`, иначе закрытие вопроса и задачи разойдётся. Обновить доску/рабочее место только там, где это уместно, с теми же правилами видимости.

### Уведомления

События: назначен вопрос, получен ответ, вопрос проверен/отклонён, обнаружена критическая сверка, остаток устарел. Использовать существующий `NotificationLog` и каналы. Текст для неправомочного пользователя не содержит себестоимость, маржу, закупочную сумму или полные реквизиты.

### Закрытие цикла

Ответ не равен изменению источника. После проверки ФД ответственный владелец источника вносит изменение через соответствующий модуль. В вопросе сохраняется `source_update_ref`, затем проекция пересобирается и расхождение закрывается.

## 13. Файлы и документы

- банковская выписка, подтверждение платежа, первичный документ и файл ответа — через существующий `Attachment`/storage и `file_response`;
- доступ к скачиванию проверяется на уровне связанного финансового объекта;
- не создавать открытые статические URL;
- файл импорта не попадает в публичный репозиторий;
- XLSX export формируется существующим принятым в проекте способом;
- в аудите хранить ID/имя файла и hash при необходимости, но не секретное содержимое.

## 14. Frontend-интеграция

### `App.tsx`

Добавить:

```tsx
{can(me, "finance_analytics") && <NavLink to="/finance">Финансы</NavLink>}

```

Реальный код должен использовать существующий импорт `can` или эквивалент из `types.ts`. Не копировать проверку ролей вручную.

Рекомендуемый порядок: «Сводка» → «Финансы» → «Контрагенты» → «Юридический блок».

### Ссылки из сделки

- `ExecutionTab`: «Открыть платёж в Финансах» по `finance_obligation_id`;
- `PlanFactTab`: «Экономика в Финансах»;
- `DealCard`: при необходимости компактная ссылка в фазе «Контракт и исполнение», без новой дублирующей вкладки;
- неправомочным пользователям ссылки не показываются, а сервер всё равно проверяет доступ.

### Ссылки из юридического блока и запчастей

- договор → его обязательства;
- заказ поставщику → связанные расходные обязательства;
- заявка запчастей → ожидаемые поступления;
- возврат к исходному объекту через существующие URL.

### API и типы

Использовать `api.ts`, `Me.perms`, `can`, существующие `ApiError`, `fmtDate`. Для мультивалютных значений добавить общий `fmtMoney(amount,currency)` рядом с существующими форматтерами, не выводить `₽` всем суммам.

## 15. Backend-регистрация и схема

- импортировать и зарегистрировать `finance.router` в центральном списке `main.py`;
- импортировать новые модели до `create_all`;
- dev `init_db()` может создать новые таблицы и добавить nullable FK-столбцы существующим моделям;
- не расширять автоматический `add_missing_columns()` до изменения типов/drop;
- production migration должен быть явным и reviewed;
- фоновые задачи не запускают полную финансовую миграцию при старте API;
- настройки Caddy, GitHub Actions, secrets и deploy не менять, если это не отдельная необходимая задача с безопасным diff.

## 17. Миграционная сверка источников

До и после миграции сформировать отчёт:

- количество строк по каждому источнику;
- активные forecast/contractual/operational строки;
- суммы по валютам и направлениям;
- количество и суммы замещённых forecast-дублей;
- количество legacy payment claims;
- связанные/не связанные `PlanFactEntry`;
- конфликты договор ↔ этап;
- операции без счёта и обязательства без даты/валюты;
- контрольный hash утверждённых версий и условий подписанных договоров до/после — должен совпасть;
- список всех ручных решений ФД по сопоставлению.

Production rollout допускается только после просмотра этого отчёта ответственным владельцем системы. Dry-run и отчёт входят в deliverable реализации, но реальные рабочие данные в архив спецификации не включаются.
