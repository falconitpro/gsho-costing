# Поэтапный план внедрения

## 1. Правила выполнения

- Работа ведётся в актуальном репозитории, без standalone-заготовки.
- Этапы выполняются последовательно; следующий не маскирует незавершённые проверки предыдущего.
- Делается небольшой логичный commit на этап. Не выполнять force-push. Итоговый PR — непосредственно в `main`, слияние только владельцем.
- Production deploy, production migration, seed и изменение секретов не входят в автоматическое выполнение.
- После каждого этапа обновляются `09_Журнал_решений.md`, `10_Состояние_внедрения.md`, список файлов и фактические результаты проверок.
- Если актуальный репозиторий отличается от базового, сначала адаптируется карта, а не откатывается код.

## 2. Этап 0 — аудит и воспроизводимая исходная база

### Работы

1. Зафиксировать ветку, commit, состояние рабочего дерева и актуальные PR-изменения затрагиваемых модулей.
2. Прочитать весь пакет и сопоставить его с текущим кодом по `03_Карта_интеграции_CRM.md`.
3. Скопировать спецификации в `docs/finance/`.
4. Поднять изолированную тестовую PostgreSQL БД и тестовое файловое хранилище без production secrets.
5. Запустить существующие backend profile tests, frontend typecheck/build.
6. Записать исходные ошибки и пропуски отдельно от ошибок внедрения.
7. Проверить наличие реальной Alembic/production migration инфраструктуры.

### Результат

- подтверждённая карта интеграции;
- baseline tests с командами и результатами;
- список предполагаемых файлов;
- список блокеров окружения;
- никаких изменений бизнес-данных.

### Gate

Нельзя считать исходный тест пройденным, если он был пропущен из-за отсутствия `DATABASE_URL`. Либо поднять тестовую БД и выполнить его, либо явно зарегистрировать блокер.

## 3. Этап 1 — финансовое ядро и аддитивная схема

### Работы

1. Добавить модели `FinanceAccount`, `FinanceBalanceSnapshot`, `FinanceObligation`, `FinanceTransaction`, `FinanceAllocation`, `FinanceRecognitionEvent`, `FinanceFxOperation`, `FinanceImportBatch`, `FinanceQuestion` и технические source-link записи по необходимости.
2. Добавить nullable связи `ExecutionStage`/`PlanFactEntry`, если выбраны итоговой архитектурой.
3. Реализовать Decimal money helpers, валютные и округляющие правила.
4. Реализовать constraints, idempotency, статусные переходы и сторнирование ядра.
5. Подготовить dev schema support и reviewed production migration path без запуска на рабочей БД.
6. Зарегистрировать модели до `create_all`, не добавляя seed.

### Тесты

- Decimal и округление;
- уникальность источника/idempotency;
- ограничения posted transaction;
- allocation sums;
- reversal;
- отсутствие destructive schema diff;
- повторный dev init без дублирования/ошибок.

### Gate

Схема и доменные инварианты проверены на чистой и на базовой копии тестовой БД. Production migration не объявляется готовой, если реального контура нет.

## 4. Этап 2 — адаптеры источников и read-only календарь

### Работы

1. Реализовать projection service и dry-run rebuild.
2. Подключить утверждённые расчёты и активные договоры через `legal_contracts.schedule()`.
3. Подключить `PurchaseOrder.payments`, `Batch.payments` и ожидаемые поступления запчастей без даты.
4. Реализовать замещение forecast договором и очередь неоднозначных соответствий.
5. Добавить связь платёжных этапов с обязательствами; для новых строк прекратить агрегирование нескольких платежей.
6. Реализовать `/api/finance/obligations`, карточку, explanation и объектные права.
7. Создать `/finance` с работающими «Обзор» в базовом объёме и «Платёжный календарь»; остальные вкладки не показывать как готовые до их реализации либо честно обозначить этап без мёртвых CTA.

### Тесты

- каждая строка нескольких авансов отдельно;
- юридическая дата против оперативного прогноза;
- forecast замещён договором без двойного итога;
- PO/Batch/Parts попадают по правилам;
- повторный rebuild не меняет counts/sums;
- изменение источника с разнесением создаёт conflict;
- object-level доступ и фильтрация.

### Gate

На контрольном наборе проект выдаёт воспроизводимый реестр, counts/sums совпадают с источниками, нет активных доказанных дублей. Первый UI уже использует реальный API.

## 5. Этап 3 — первый полный вертикальный срез факта

### Сквозной сценарий

Подписанный договор → две и более отдельные строки → финансовый счёт и подтверждённый остаток → банковская операция → частичное разнесение на одну строку → вторая операция → закрытие остатка → ссылки на сделку/договор → аудит.

### Работы

1. Счета на базе own `BankProfile` и balance snapshots.
2. Ручной ввод, post и reverse банковских операций.
3. Provisional/confirmed allocations, many-to-many и защита от превышения.
4. UI счёта/операции/разнесения в «Ликвидность и валюта» и карточке обязательства.
5. Старые payment entry points перевести на `needs_reconciliation` adapter без фиктивного posted факта.
6. Базовая очередь сверки legacy payment claims.
7. Ссылки из `ExecutionTab` и юридической карточки.

### Тесты

- частичная оплата двумя операциями;
- одна операция на два обязательства;
- повтор idempotency;
- гонка разнесения;
- сторно уменьшает подтверждённый факт корректно;
- legacy отметка не меняет подтверждённый остаток;
- менеджер/КД без EDIT не могут выполнить mutation;
- полный браузерный сценарий.

### Gate

Это первый функциональный milestone. Не переходить к масштабированию, если сквозной сценарий не работает в браузере и API одновременно.

## 6. Этап 4 — импорт, ликвидность и валюта

### Работы

1. CSV/XLSX import preview/confirm, file hash, external refs и ошибки строк.
2. Остатки по счетам на дату, unknown balance, устаревание снимков.
3. Прогнозная кривая по дням/неделям с ненулевым входящим остатком.
4. Мультивалютность и RUB-консолидация с явными курсами.
5. Двухногая конвертация и комиссии.
6. Кассовые разрывы, undated/unallocated/needs_reconciliation вне кривой.
7. `/api/summary/money` как adapter и рабочее место на общем сервисе.
8. `/summary?kind=money` compatibility и ссылка «Финансы» на рабочем месте.

### Тесты

- повторный импорт;
- смешанные валюты;
- opening balance;
- posted против forecast;
- конвертация без P&L;
- отсутствие даты;
- совпадение Finance/Workplace/Summary DTO;
- прежние summary role tests;
- график, таблица, экспортная выборка и браузерные проверки.

### Gate

Нет кривой от фиктивного нуля. Одинаковые фильтры во всех трёх представлениях дают одинаковые суммы. Старые ссылки работают.

## 7. Этап 5 — экономика, признание и юридические сводки

### Работы

1. Recognition events и deal-scoped права ввода.
2. Обновить план/факт: revenue по признанию, expense по статьям, cash отдельно, фактический cash gap.
3. Мигрировать/связать старые `PlanFactEntry` без дублей.
4. Построить «Экономика сделок» на текущем расчётном движке.
5. Построить «Обеспечение и неустойки» на `legal_contracts.obligations()`.
6. Признанные/предъявленные неустойки с датой подключить к прогнозу; начисляемые не включать автоматически.
7. Обновить `PlanFactTab` и обратные ссылки.

### Тесты

- входящий платёж не создаёт выручку;
- expense recognition по статье;
- legacy cost item мигрирует один раз;
- stage-linked PlanFactEntry не дублируется;
- фактический cash gap при достаточных данных;
- подписанные условия и hash утверждённых версий не изменились;
- неустойки по статусам и датам;
- CD/FD/GD видят экономику, неправомочные не получают её через API/export.

### Gate

План, прогноз, P&L fact и cash fact различимы и объяснимы. Старый план/факт не ослаблен, закрытие ФД работает.

## 8. Этап 6 — сверка, вопросы и экспорт

### Работы

1. Все очереди сверки и ручные решения с аудитом.
2. Детерминированное «Объяснить цифру» для агрегатов и строк.
3. `FinanceQuestion`, scoped answer, task-like интеграция `/api/tasks/my`, уведомления и файлы.
4. Проверка ответа и последующее обновление канонического источника.
5. XLSX exports из авторизованных read services.
6. Полировка loading/empty/error/confirm, адаптивности и клавиатуры.

### Тесты

- scoped доступ ответственного;
- отсутствие чувствительных полей в task/notification/question/export;
- полный цикл вопроса;
- explanation повторяемость;
- экспорт совпадает с экраном;
- XLSX formula injection;
- все кнопки и ссылки.

### Gate

Нет мёртвых элементов. Ответственный без финансового права может ответить, но не видит финансовый контур. Экспорт не расширяет права.

## 9. Этап 7 — миграционная репетиция и полный QA

### Работы

1. Сделать копию анонимизированного/тестового среза базовой БД.
2. Записать контрольные counts/sums/hash до миграции.
3. Выполнить schema migration и finance rebuild в dry-run.
4. Просмотреть конфликты, выполнить только доказанные автоматические связи.
5. Повторить rebuild и проверить идемпотентность.
6. Сформировать финальный миграционный отчёт без секретов.
7. Запустить все backend tests, frontend typecheck/build и браузерный чек-лист `07`.
8. Проверить 1440/1280/768/390 px и сделать скриншоты.
9. Проверить console/network и все основные ссылки.
10. Подготовить PR в `main` с описанием, миграциями, тестами, ограничениями и rollout/rollback планом.

### Gate

- нет неучтённых расхождений;
- нет изменений утверждённых расчётов и подписанных условий;
- нет дублей после повторной миграции;
- нет незадокументированных пропущенных тестов;
- нет новых console errors/404;
- журнал состояния отражает факт;
- production rollout не выполнен автоматически.

- несвязанные изменения страницы входа или глобального дизайна.

## 11. Rollout и rollback

### Rollout, только отдельным подтверждением владельца

1. Backup и проверка восстановления.
2. Применение reviewed additive migration в maintenance window.
3. Dry-run/rebuild и сверка counts/sums.
4. Включение read-only Finance.
5. Проверка compatibility Summary/Workplace.
6. Поэтапное включение факта, импорта и редактирования.
7. Мониторинг ошибок и очереди сверки.

### Rollback

- откат приложения не должен удалять новые финансовые таблицы и историю;
- старые compatibility adapters должны позволять безопасно вернуть прежний UI;
- данные, уже внесённые как posted/reversed, не переписываются скриптом отката;
- повторный rollout использует idempotency keys;
- destructive rollback migration не создавать по умолчанию.

## 12. Отчёт после каждого этапа

Использовать `11_Шаблон_отчёта_этапа.md`. Обязательно указать фактические команды и результаты, а не «должно работать». Если диалог продолжается правкой, следующий шаг начинается с чтения этого отчёта и текущего diff.
