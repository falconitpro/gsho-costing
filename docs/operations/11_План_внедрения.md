# Поэтапный план end-to-end внедрения

## 1. Правила выполнения

- Работа ведётся в текущем репозитории, каждая ветка от актуального `main`, PR непосредственно в `main`.
- Владелец сливает PR и выполняет облачные/production действия. Claude не сливает сам и не меняет панели.
- Этап завершён только после фактических tests/build/browser checks, обновления журналов и отчёта `17`.
- Не скрывать pre-existing failures: сравнить с чистым baseline и описать.
- Миграции применяются вручную после rehearsal и backup. Не запускать production deploy автоматически.
- Не отключать Timeweb до restore gate.

## 2. Этап 0 — baseline и защита исходного состояния

**Ветка:** не требуется, если только аудит; для docs — `chore/operations-baseline`.

Действия:

1. Проверить `origin/main`, diff от `e652a88…`, список migrations выше 009.
2. Поднять чистую PostgreSQL 16 и synthetic test environment.
3. Применить существующие SQL change set’ы дважды на rehearsal DB, зафиксировать фактический результат; не менять старые файлы ради «красоты» без отдельной причины.
4. Запустить исходные backend tests, frontend typecheck/build, существующий CI.
5. Инвентаризировать auth/upload/download/export/notification/deploy точки по `08`.
6. Записать текущие backup volumes, размер БД/файлов и ресурсы ВМ без выгрузки реальных данных в диалог.
7. Проверить план хранения секретов владельца.

**Gate:** baseline воспроизводим, список pre-existing issues составлен, нет неизвестного нового migration collision.

## 3. Этап 1 — Yandex backup code и инструкции

**Ветка:** `feat/yandex-backup`.

Вертикальный срез:

- `010_backup_operations.sql`, BackupRun;
- scripts/service/timer/env example/install;
- sanitized host status + API + UI;
- failed/stale in-app notifications;
- docs runbook, restore gate;
- изменения deploy подготовлены, но обязательный pre-deploy hook не включён до настройки.

Проверки:

- bash -n/shellcheck, unit tests status parser;
- локальный synthetic restic repository integration;
- отдельный Yandex test bucket либо владелецский controlled test после создания секретов — без вывода ключей;
- timer calendar 19:00 Moscow и Persistent;
- simulated S3/network/disk failure, lock/concurrency, staging cleanup;
- двукратная миграция;
- browser status/error/forbidden.

PR не удаляет старый Compose backup.

**Действия владельца после merge/deploy:** создать bucket/SA/keys, записать protected env, запустить manual/daily, предоставить sanitized status.

**Gate 1:** ручная копия успешна, два последовательных daily успешны, check успешен. Затем recovery drill по `13`.

## 4. Этап 2 — Security core

**Ветка:** `feat/security-core`.

Порядок внутри:

1. AuthSession + sid + logout/revoke + own sessions UI.
2. Password policy/history/must-change.
3. MFA TOTP/recovery/optional policy.
4. Offboarding service и подключение всех is_active paths.
5. Access review + notifications.
6. Security admin UI и safeguards.

Проверки:

- все существующие auth tests + новые role matrix;
- revoked cookie сразу 401;
- MFA optional/required/OIDC cases;
- concurrent offboard, rollback, last admin;
- SQL `011` дважды;
- browser 4 widths, no lockout владельца.

Rollout:

- сначала optional MFA;
- владелец и резервный admin настраивают MFA/recovery;
- migration window старых JWT явно ограничен;
- после отчёта владелец подтверждает required.

**Gate 2:** обязательные auth/security тесты пройдены, владелец подтвердил наличие восстановительного доступа.

## 5. Этап 3 — Security audit и файлы

**Ветка:** `feat/security-audit-files`.

Срез:

- SecurityEvent/Alert + thresholds + UI;
- инвентаризация и подключение всех exports/downloads;
- quarantine + ClamAV + status + orphan cleaner;
- protected attachment download и S3 <=300 sec;
- `012` migration;
- resource limits и recovery/test safety checks.

Проверки:

- EICAR standard test по безопасной политике, clean/infected/error/pending/legacy;
- scanner down fail-closed;
- zip/archive/parser limits;
- RAM/CPU на production-подобной 2 vCPU/4 ГБ;
- denied/IDOR и события без secret canaries;
- S3 URL expiry, no public anonymous;
- all exports audit, alert thresholds/dedup;
- browser scan states and alerts.

**Gate 3:** нет bypass, нет OOM, новые файлы не выдаются до clean, старые данные не заблокированы массово.

## 9. Этап 7 — Сквозная приёмка

**Ветка:** `feat/operations-final-qa`.

- Объединённый regression suite на чистой synthetic PostgreSQL.
- Все роли и ключевые существующие модули: deals, legal, parts, finance, tasks, notifications.
- Browser QA по `12`, console/network, accessibility.
- Migration rehearsal 010–015 в фактически планируемом production порядке, повторное применение.
- Recovery drill повторно на итоговом коде, если security schema менялась после первого drill — обязательно повторить.
- Нагрузочный smoke backup+scanner+backend на ресурсах ВМ.
- Актуализация docs, журналов, owner checklist.

**Gate 7:** владелец принимает результаты и отдельно подтверждает переход.

## 10. Этап 8 — Окончательный перенос копий и pre-deploy enforcement

Только после Gates 1 и 7 и повторного итогового restore:

1. Отдельный PR удаляет старый Compose `backup`, не volumes.
2. Включить `BACKUP_REQUIRED=true` и pre-deploy fail-fast.
3. Владелец выполняет контролируемый production deploy/migrations.
4. Проверить daily timer после reboot и следующий scheduled run.
5. Владелец вручную отключает provider backups Timeweb.
6. Контролируемая очистка старых локальных архивов по `13`, без `down -v`.
7. Зафиксировать фактическую дату: постоянные копии находятся только в Yandex; Timeweb остаётся вычислительным хостом и временным staging.

## 11. Production rollout чеклист для владельца

- [ ] Актуальный main и PRs проверены/слиты владельцем.
- [ ] Секреты созданы вне git/CRM/Claude.
- [ ] Pre-deploy Yandex backup успешен.
- [ ] Recovery backup доступен и RESTIC_PASSWORD проверен.
- [ ] Maintenance window/rollback plan согласованы.
- [ ] SQL rehearsal пройден, production apply выполнен вручную в зафиксированном порядке.
- [ ] MFA optional rollout завершён, owner/recovery admin защищены.
- [ ] ClamAV ресурсы достаточны.
- [ ] External AI policy подтверждена либо provider none.
- [ ] Почта поддержки не настраивалась.
- [ ] Smoke tests production выполнены без массовых synthetic seed и без отправки внешних сообщений.
- [ ] Timeweb backups отключены только после явного restore confirmation.

## 12. Порядок при блокировках

| Блокировка | Действие |
|---|---|
| Новый migration в main | продолжить номера, не перезаписывать; обновить mapping |
| Недостаточно RAM для ClamAV | isolated worker/лимит concurrency; fail-closed |
| Нет Yandex keys | код/tests на synthetic/local restic; production gate не отмечать выполненным |
| Restore failed | Timeweb остаётся включённым; исправить и повторить |
| Старые auth sessions incompatible | ограниченный migration window + forced re-login после backup; не bypass |
| LLM недоступен/не разрешён | provider none; help/tools/сводка продолжают работать |
| Failing baseline tests | зафиксировать, не маскировать; отдельный fix PR по согласованию |
| Пересечение с новым бизнес-PR | rebase/merge актуального main без force-push shared history, адаптировать и повторить checks |
