# Архитектура и модель данных

## 1. Принципы

1. Новые функции встраиваются в существующие FastAPI routers, SQLAlchemy models, React routes и CSS.
2. Авторизация выполняется на сервере при каждом запросе и повторно внутри каждого AI tool.
3. Бизнес-аудит остаётся в `AuditLog`; security telemetry, содержимое поддержки и содержимое AI-диалогов — разные домены с разными правами.
4. Production scheduler backup — systemd на хосте. In-process `_daily_jobs()` не является единственным scheduler для критичных копий.
5. Файлы проходят единый scan/download контур; ИИ не получает filesystem/shell/database adapter.
6. Все денежные и сроковые данные берутся из существующих сервисов. Никаких параллельных формул.
7. Модель данных аддитивна. Названия и типы ниже — обязательная проектная основа; фактические типы ID привести к текущему `VARCHAR(36)` и UUID-string convention.

## 2. Контурная схема

```text
Browser / React
  ├─ existing CRM routes ───────────────┐
  ├─ /support, /support/admin           │
  ├─ Settings → Security / Access review│
  ├─ Workplace briefing                 │
  └─ Assistant drawer                   │
                                        ▼
                              FastAPI + CurrentUser
                     effective_perms + overrides + can_see_deal
                  finance.access.Visibility + filter_payload
          ┌────────────────┬─────────────────┬────────────────┐
          ▼                ▼                 ▼                ▼
    AuthSession/MFA   Support service   Briefing service   AI orchestrator
    Offboarding       App-only notify   Existing DTOs       Allowlist tools only
    Access review     Scan/download     Finance services    Sanitized context
          │                │                 │                │
          ▼                ▼                 ▼                ▼
                       PostgreSQL 16 + local/S3 private storage

Timeweb host:
  systemd gsho-backup.timer → backup script → pg_dump/files/manifest
                                           → restic (client encryption)
                                           → Yandex Object Storage private bucket
  atomic last-run.json → read-only backend status projection → BackupRun/UI

Isolated recovery VM:
  read-only restore account → restic restore → temporary PostgreSQL/files
  APP_ENV=recovery; external mail/WeCom/LLM/deploy disabled
```

## 3. Общие соглашения

- ID: строка UUID; создание через текущий helper либо `uuid4`, без новой последовательности PK.
- Время: timezone-aware UTC `DateTime(timezone=True)`. Локальная дата срока — `Date`, если так уже принято в модуле.
- JSON: `JSONB`, default `{}`/`[]` через Python и SQL, не mutable default.
- Деньги не добавляются в новые таблицы как numeric без необходимости; AI/briefing ссылаются на существующие обязательства.
- Удаление истории: security events и системные сообщения immutable. AI conversations могут удаляться по политике retention/запросу владельца; связанные технические audit-записи сохраняются в sanitized виде.
- Внешние ключи не каскадируют удаление бизнес-истории. Пользователь не удаляется физически.
- Все list endpoints имеют pagination/limit; count queries не содержат чувствительные поля в логах.

## 4. Backup operations

### `backup_runs` — `BackupRun`

| Поле | Тип / ограничение |
|---|---|
| `id` | PK |
| `run_key` | unique, host-generated UUID |
| `reason` | `daily|pre_deploy|manual|restore_check` |
| `status` | `running|success|failed` |
| `started_at`, `finished_at` | UTC, nullable |
| `snapshot_id` | короткий безопасный идентификатор restic, nullable |
| `git_commit`, `schema_revision` | string, nullable |
| `storage_provider` | `local|s3|unknown` |
| `database_bytes`, `files_bytes` | bigint, nullable |
| `manifest_sha256` | string, nullable |
| `check_status`, `checked_at` | enum/string, UTC |
| `error_code`, `error_summary` | sanitized string, без command/env/path с секретами |
| `created_at`, `updated_at` | UTC |

Индексы: `(status, started_at)`, `(finished_at)`. Status writer принимает только заранее определённую схему JSON и не выполняет shell. Host-side `last-run.json` остаётся источником последнего состояния при недоступной БД; `BackupRun` — история и UI при доступной БД.

## 5. Security core

### `auth_sessions` — `AuthSession`

- `id` PK; `sid` unique indexed UUID, помещается в JWT;
- `user_id` FK users, indexed;
- `token_hash` unique SHA-256/HMAC хэш представленного credential, если используется дополнительная защита; исходный JWT не хранить;
- `created_at`, `last_seen_at`, `last_seen_bucket`, `idle_expires_at`, `absolute_expires_at`;
- `revoked_at`, `revoked_by`, `revoke_reason` (`logout|user|admin|password|offboard|mfa_reset|security`);
- `remember` bool; `auth_method` (`password|oidc|recovery`);
- `mfa_level` (`none|totp|oidc_verified|recovery`);
- `last_mfa_at` nullable;
- `ip_prefix`/защищённое представление IP, `user_agent_short`, `device_label`;
- `created_from_request_id`.

Индексы `(user_id, revoked_at, absolute_expires_at)`, `(last_seen_at)`. Cleanup закрытых записей по отдельной retention policy не стирает security events.

### `mfa_credentials` — `MfaCredential`

- `user_id` unique FK;
- `secret_ciphertext` encrypted, не plaintext;
- `key_id` версия ключа шифрования;
- `enabled_at`, `created_at`, `last_used_at`;
- `failed_attempts`, `locked_until`;
- `pending_secret_ciphertext`, `pending_expires_at` — либо отдельная short-lived запись; никогда не включать в `mfa_enabled=true` до подтверждения.

### `mfa_recovery_codes` — `MfaRecoveryCode`

`id`, `user_id`, `code_hash`, `created_at`, `used_at`, `used_session_id`. Код и секрет не логируются.

### `password_history` — `PasswordHistory`

`id`, `user_id`, `password_hash`, `created_at`; unique `(user_id, password_hash)`. Хранить минимум 5 последних; не хранить password text.

### `security_events` — `SecurityEvent`

- `id`, `occurred_at`, `actor_user_id` nullable, `subject_user_id` nullable;
- `event_type`, `action`, `result` (`success|denied|error`);
- `request_id`, `session_id`, `ip_prefix`;
- `entity_type`, `entity_id`, `deal_id` nullable;
- `format`, `row_count`, `byte_size` nullable;
- `metadata` sanitized JSONB, `risk_score` optional;
- `alert_id` nullable.

Индексы `(actor_user_id, event_type, occurred_at)`, `(subject_user_id, occurred_at)`, `(occurred_at)`, `(deal_id)`. Запрет UPDATE/DELETE на уровне приложения и отдельной DB role; production app role не должна иметь право обхода audit controls без необходимости.

### `security_alerts` — `SecurityAlert`

`id`, `rule_key`, `severity`, `status new|acknowledged|resolved`, `subject_user_id`, `first_seen_at`, `last_seen_at`, `occurrence_count`, `summary`, `details_sanitized`, `acknowledged_by/at`, `resolved_by/at`, `resolution_comment`.

Unique/dedup strategy: `(rule_key, subject_user_id, open status)` через поиск активной записи в транзакции; при новом окне после resolved создаётся новая запись. Пороги — защищённые settings, не клиентские параметры.

### Access review

`access_review_campaigns`: `id`, `title`, `period_start/end`, `due_date`, `status draft|open|completed|cancelled`, `created_by`, `created_at`, `completed_at`.

`access_review_items`: `id`, `campaign_id`, `user_id`, `snapshot` JSONB, `decision pending|keep|change|disable`, `reviewer_id`, `reviewed_at`, `comment`, `completed_at`. Unique `(campaign_id, user_id)`. Snapshot не содержит password/MFA/session tokens.

### Аддитивные изменения существующих таблиц

- `users`: `password_must_change bool default false`, `mfa_enforced_at` nullable при необходимости, `offboarded_at`, `offboarded_by` nullable.
- `tasks`: `needs_reassignment bool default false`, index по `(assignee_id, needs_reassignment)`; не менять существующие `done_at/due` semantics.
- `access_user_overrides`: использовать существующий `valid_to` для отключения; не добавлять дублирующий статус, если он не нужен.

## 6. File scanning

### `attachment_scans` — `AttachmentScan`

- `id`, `attachment_id` nullable до promote, `quarantine_key` internal unique;
- `status pending|clean|infected|error|legacy_unscanned`;
- `engine`, `engine_version`, `signature_version`;
- `sha256`, `size`, `detected_name` sanitized;
- `attempts`, `last_error_code`, `scanned_at`, `created_at`, `updated_at`.

Индексы `(status, created_at)`, unique attachment_id после связывания. Для старых `attachments` можно добавить `scan_status` default `legacy_unscanned` и `scanned_at`, чтобы избежать дорогого join в hot path; окончательный вариант выбрать после explain, но статус должен быть атомарно согласован с доступностью.

Правила:

- quarantine вне public/storage served root, unpredictable name, минимальные права ОС;
- promote + attachment + clean status в одной БД-транзакции настолько, насколько позволяет filesystem; orphan cleaner устраняет рассинхронизацию;
- infected/error не доступны по старому пути;
- scanner API не принимает произвольный host path от клиента;
- download authorization проверяется до scan status и до выдачи S3 URL.

## 7. Support

### `support_tickets`

- `id`, `number` unique (`SUP-YYYY-NNNN`);
- `reporter_id` FK, indexed; `assignee_id` nullable;
- `category error|question|access|improvement`;
- `requested_urgency normal|high|critical`, `priority low|normal|high|critical`;
- `subject`, `description`, `current_route`;
- `app_commit`, `correlation_id`, `client_metadata` sanitized JSONB;
- `status new|in_progress|waiting_reporter|resolved|closed`;
- `first_response_at`, `resolved_at`, `closed_at`, `last_activity_at`;
- `created_at`, `updated_at`, `reopened_from_id` nullable.

Индексы `(reporter_id, last_activity_at)`, `(status, priority, last_activity_at)`, `(assignee_id, status)`. Номер создаётся в БД-транзакции через `support_number_sequences(year PK, next_value)` и `SELECT FOR UPDATE`; retry на serialization/deadlock. Нельзя использовать count+1.

### `support_messages`

`id`, `ticket_id`, `author_id` nullable для system, `kind user|specialist|system`, `body`, `created_at`. Сообщения immutable; system body генерируется сервером из события, не принимается клиентом.

### `support_attachments`

`id`, `ticket_id`, `message_id` nullable, `attachment_id` unique FK existing attachments, `uploaded_by`, `created_at`. Existing `Attachment.entity="support_ticket"`, `entity_id=ticket.id`; `deal_id=null`. Доступ проверяется через ticket reporter/support_admin, а не `can_see_deal`.

## 8. AI assistant

### `ai_conversations`

`id`, `owner_id`, `title`, `default_mode crm|help|general`, `created_at`, `updated_at`, `last_message_at`, `deleted_at`. Все остальные таблицы наследуют доступ от владельца conversation.

### `ai_messages`

`id`, `conversation_id`, `role user|assistant|system_notice`, `mode`, `content`, `content_sanitized` при необходимости, `status complete|fallback|error`, `provider`, `model`, `sources` JSONB фактических citations, `warnings` JSONB, `request_id`, `created_at`. Не хранить hidden chain-of-thought. Можно хранить короткое пользовательское содержимое только при включённой истории и предупреждении пользователя.

### `ai_tool_audits`

`id`, `conversation_id`, `message_id`, `actor_user_id`, `tool_name`, `arguments_sanitized`, `result_status`, `result_count`, `entity_ids` limited JSONB, `duration_ms`, `error_code`, `created_at`. Полный чувствительный result payload не хранить.

### `ai_feedback`

`id`, `message_id`, `user_id`, `rating positive|negative`, `comment`, `created_at`. Unique `(message_id,user_id)`.

### `ai_usage_daily`

`user_id`, `usage_date`, `request_count`, `token_in`, `token_out`, `updated_at`, PK `(user_id, usage_date)`. Инкремент атомарный; лимит проверяется до внешнего вызова.

## 9. Briefing

### `briefing_item_states`

- `id`, `user_id`, `item_key`, `source_signature`;
- `pinned_at`, `snoozed_until`, `hidden_at`;
- `created_at`, `updated_at`;
- unique `(user_id,item_key,source_signature)`.

`item_key` стабилен по типу и реальному source ID (`task:<id>`, `obligation:<id>`, `support:<id>`). `source_signature` — SHA-256 канонического набора значимых полей: статус, срок, сумма/остаток, assignee. Не включать секреты и полное содержимое.

Сама сводка не обязана храниться: `briefing.build()` вычисляет её свежо. Если нужен snapshot для метрик, отдельная `briefing_snapshots` без чувствительных payload; первый срез его не требует.

## 11. SQL change set’ы

Начать после `009_mirror_parts_rfq.sql`:

- `010_backup_operations.sql`: `backup_runs`, indexes;
- `011_security_core.sql`: sessions, MFA, password history, access review, additive users/tasks;
- `012_security_audit_files.sql`: security events/alerts, scans, additive attachments;
- `013_support.sql`: support tables, sequences, indexes;
- `014_assistant.sql`: AI tables/usage/indexes;
- `015_briefing.sql`: briefing item states.

Каждый файл:

1. `BEGIN`;
2. только `CREATE TABLE IF NOT EXISTS`, `ALTER TABLE … ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`;
3. CHECK constraints добавляются идемпотентно через явно проверенный DO-блок либо валидацию на приложении; не дублировать constraint при повторном запуске;
4. defaults не изменяют смысл существующих строк;
5. `COMMIT`;
6. smoke SQL проверяет columns/indexes, insert/select/rollback на синтетике;
7. второй прогон даёт тот же результат;
8. production apply — отдельная ручная операция после pre-deploy backup и rehearsal.

## 12. Надёжность и конкурентность

- Токен session validation: БД-проверка обязательна; короткий cache допускается только с немедленным cache invalidation при revoke и тестом гонки. Для security-critical revoke кэш не должен оставлять доступ.
- Offboarding блокирует user row `SELECT FOR UPDATE`; все связанные отзывы происходят в той же транзакции БД. Внешние cache invalidations после commit, с fail-safe revoke version.
- Support number и AI daily quota — атомарные DB операции.
- Backup lock — `flock`; повторный timer не запускает вторую копию.
- Scan worker использует leases/attempts, не берёт один файл бесконечно; timeout и retry limit видимы.
- Внешние вызовы S3/ClamAV/LLM имеют deadline, retry только для безопасных idempotent операций и понятный sanitized error.
