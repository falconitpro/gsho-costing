# Безопасность и права сотрудников

## 1. Цель и порядок внедрения

Цель — предотвратить незаметное использование старых входов, чрезмерные права, утечку документов и небезопасную работу с файлами, сохранив существующую бизнес-логику CRM.

Два обязательных среза:

1. **Security core:** server-side sessions, MFA, пароли, offboarding, пересмотр прав.
2. **Security audit & files:** журнал скачиваний/выгрузок, алерты, антивирусный карантин, короткие приватные ссылки, изоляция recovery/test/AI.

Нельзя включать только красивые экраны: отзыв сессии, offboarding и доступ к файлу должны подтверждаться серверными негативными тестами.

## 2. Единая модель аутентификации

### 2.1 Текущая основа

Сохранить HttpOnly-cookie `gsho_session`, текущий password/OIDC flow и claim `pv`. Добавить `sid` и обязательную запись `AuthSession`. Старый stateless JWT без `sid` допускается только в коротком явном migration window по решению владельца; после rollout такие токены недействительны. Не оставлять постоянный fallback «если таблицы нет — пропустить».

### 2.2 Выдача и проверка

При входе:

1. Проверить пользователя, активность, lockout и пароль/OIDC.
2. Если требуется MFA — создать отдельный короткий `mfa_pending`, не выдавать CRM cookie.
3. После второго фактора создать `AuthSession` и JWT с `sub`, `sid`, `iat`, `exp`, `nonce`, `pv`, `mfa`.
4. Установить cookie `HttpOnly`, `Secure` на HTTPS, `SameSite=Lax` либо более строгий проверенный вариант; OIDC CSRF state/nonce сохранить.
5. Создать security event без credential.

При каждом запросе `get_current_user`:

- подпись, issuer/audience при наличии, `exp`, `sub`, `sid`, `pv`;
- session существует, принадлежит пользователю, `revoked_at IS NULL`;
- пользователь активен;
- текущее время меньше idle и absolute expiry;
- MFA policy выполнена;
- обновить last_seen/idle максимум раз в 60 секунд;
- для security-sensitive action проверить `last_mfa_at` не старше 10 минут.

Обычная сессия: idle 8 часов и отдельный absolute limit 24 часа. Remember: до 30 дней, absolute 30 дней, но любой серверный revoke действует немедленно. Это изменение absolute limit согласовать в отчёте, не сделать скрыто.

### 2.3 Logout и revoke

- Logout отзывает текущий `sid` в БД и удаляет cookie; даже если cookie повторно отправлен, сервер возвращает 401.
- «Завершить сессию» доступно владельцу сессии или security admin.
- «Завершить все, кроме текущей» меняет все остальные `revoked_at` атомарно.
- Password reset, MFA reset, offboarding отзывают все сессии.
- Session list не возвращает JWT, token hash, cookie, recovery code и полный sensitive user-agent fingerprint.
- Повторный revoke идемпотентен и не создаёт ложное «успешно завершено» для несуществующей сессии.

## 3. MFA

### 3.1 Настройка пользователем

1. Пользователь вводит текущий пароль либо проходит recent step-up.
2. Backend создаёт pending secret, хранит его зашифрованным и выдаёт otpauth/QR только в этом защищённом ответе.
3. Пользователь вводит 6-значный код.
4. Backend проверяет код, активирует credential, генерирует 10 recovery codes и показывает их один раз.
5. Сохраняются только хэши codes; текущая сессия получает подтверждённый MFA level; событие журналируется.

Повторная настройка не должна незаметно затереть действующий MFA до успешной проверки нового секрета. При незавершённой настройке pending истекает.

### 3.2 Вход

- `mfa_pending` — отдельный одноразовый challenge с ID, user ID, expiry 5 минут, attempts и hashed verifier. Не использовать полноценный `gsho_session`.
- Rate limit по challenge, user и IP; не сообщать, какой именно фактор неверен, сверх необходимого UX.
- Recovery code можно использовать вместо TOTP; после использования показать оставшееся количество и создать security event.
- Часы сервера синхронизируются по NTP; допустимый skew минимален и документирован.
- При недоступности шифровального MFA key новый вход не переводится в bypass. Восстановление доступа — контролируемая процедура владельца.

### 3.3 Rollout

- Сначала `MFA_POLICY=optional`; ЗГД и security admins включают первыми.
- Проверить TOTP, recovery, lockout, OIDC, remember, logout и offboarding.
- После подтверждения владельца — `required`.
- В required режиме пользователь без MFA получает только `/auth/me`, MFA setup/verify и logout. Остальные endpoints закрыты на сервере, не только скрыты в меню.
- OIDC: принять внешний MFA только при проверенном `amr/acr` и документированной корпоративной политике. Один признак наличия OIDC не равен MFA.
- Отдельный break-glass аккаунт владельца: аппаратно/внешне защищённые recovery codes, минимальное использование, отдельный alert. Не оставлять общеизвестный пароль.

## 4. Пароли и хэши

Проверка сложности — единый server helper, применяемый при регистрации/создании, смене, admin reset и первичном входе:

- длина 12–128;
- хотя бы одна буква и одна цифра;
- не входит в локальный список распространённых/скопометрированных паролей;
- не совпадает с email/login/именем и не состоит из них с тривиальными цифрами;
- не совпадает с текущим и последними пятью хэшами через безопасное сравнение verify;
- ошибки формы понятны, но не раскрывают существование чужого аккаунта.

PBKDF2-стойкость повышается только после benchmark на production-подобных 2 vCPU: измерить p50/p95 login latency и CPU. При увеличении iterations записывать параметры в hash format, старые hashes проверять, после успешного входа делать rehash. Не сбрасывать все пароли массово.

Admin reset:

- генерирует временный пароль, не возвращает его в общем журнале;
- `password_must_change=true`;
- отзывает все сессии;
- доступ после входа ограничен сменой пароля/MFA;
- старый пароль больше не работает.

## 5. Offboarding как единая операция

### 5.1 API и триггеры

Создать `POST /api/security/users/{user_id}/offboard`. Обычные существующие admin/team endpoints при переходе `is_active: true → false` обязаны вызывать тот же service, а не выполнять частичное обновление. Нельзя оставить второй путь, который оставляет сессии активными.

### 5.2 Транзакция

1. Проверить `security_admin=EDIT`, recent MFA step-up и подтверждение фамилии/имени сотрудника.
2. `SELECT users FOR UPDATE`; запрет self-offboard и отключения последнего активного security admin.
3. Установить `is_active=false`, `offboarded_at/by`.
4. Отозвать все AuthSession и MFA challenges.
5. Завершить активные replacements/delegations, где пользователь — обе возможные стороны.
6. Установить `valid_to=now` для действующих AccessUserOverride; прошлые записи не переписывать.
7. Открытые назначенные задачи отметить `needs_reassignment=true`.
8. Назначенные support tickets снять с assignee и добавить system message.
9. Открытые finance questions не закрывать автоматически; включить в отчёт/очередь ответственного модуля.
10. Создать AuditLog и SecurityEvent с counts и request ID.
11. Commit; затем очистить auth/access caches и отправить app-only уведомления ответственным.

Если любой обязательный шаг БД упал, rollback всей операции. Не показывать успех при частичном отключении.

### 5.3 После отключения

- Повторный запрос с прежним cookie — 401.
- Пользователь остаётся в истории, авторстве и фильтрах как «Доступ отключён».
- Открытые бизнес-задачи видны security/ответственным руководителям как требующие переназначения, но автоматически не передаются случайному сотруднику.
- Повторная активация требует `security_admin=EDIT`, отдельного подтверждения, проверки ролей и нового входа/MFA. Старые sessions не воскрешаются.

## 6. Пересмотр прав

### 6.1 Кампания

По умолчанию ежеквартально. Security admin создаёт кампанию на всех активных пользователей либо выбранное подразделение. Snapshot включает:

- роль и активность;
- эффективные группы прав;
- user overrides, их действие и сроки;
- observer scope;
- acting_for/delegations;
- support/security/assistant/backup permissions;
- MFA enabled и дата последнего входа, без секретов.

### 6.2 Решение

`keep` — без изменений; `change` — ссылка/набор реально выполненных изменений; `disable` — вызов offboarding. Reviewer не может в одиночку утвердить повышение собственных прав; нужен второй уполномоченный reviewer. Для last admin применяется тот же safeguard.

Напоминания только в app: за 14, 7 и 1 день; просрочка — security alert. Dashboard показывает процент проверенных, просроченные, пользователей с чрезмерными срочными overrides. Завершение кампании возможно, когда по каждому item есть решение либо явный документированный пропуск по решению владельца; не скрывать остаток.

## 7. Журнал скачиваний и выгрузок

### 7.1 Инвентаризация

До реализации составить список всех endpoints:

- `GET /api/files/{path:path}` и другие attachment download/preview routes;
- S3 link/presign methods;
- XLSX/DOCX/PDF exports, finance exports, imports results;
- mass list export и deal version downloads;
- support attachments;
- любые generated file responses.

Для каждого указать auth function, deal/entity visibility, scan enforcement, security event. Не закрыть только один известный route, оставив bypass.

### 7.2 Событие

Успех и отказ фиксируются после авторизации/попытки. Metadata: фильтры whitelist’ом, row count, format, entity IDs, byte size, request ID. Не записывать содержимое, подписанный URL с query signature, cookie, Authorization, пароль, TOTP, полный document text и необработанный request body.

Для denied event actor может быть не аутентифицирован; IP хранится в принятом сокращённом/защищённом виде. События не должны ломать основной download при кратковременном сбое telemetry? Для security mutations audit обязателен транзакционно. Для download telemetry выбрать fail-safe: ошибка журнала security-critical export блокирует выгрузку; обычный inline image может иметь отдельную документированную политику, но нельзя молча отбрасывать события. Рекомендуемый единый вариант для закрытых документов и экспортов — fail-closed с понятной 503.

### 7.3 Алерты

Правила версионируются и хранятся на сервере. Начальные:

| Правило | Начальный порог | Severity |
|---|---:|---|
| Частые экспорты | >5 за 10 минут | high |
| Крупный экспорт | >=1000 строк | medium/high |
| Частые скачивания | >20 закрытых файлов за 10 минут | high |
| Изменение доступа | каждое | high |
| MFA reset/offboard | каждое | critical/high |
| Повторные denied | настраиваемый порог | medium |

Первый срез предупреждает, не блокирует обычную работу автоматически. В alert нет закрытого содержимого; есть ссылка на security event и действие «Проверить». Acknowledge/resolve требуют комментария и журналируются.

## 8. Безопасная загрузка файлов

### 8.1 Поток

```text
Authorized request
  → size/extension/MIME precheck
  → quarantine outside served root
  → SHA-256 + real type detection
  → clamd scan with limits/timeouts
  → clean: DB attachment + scan status + promote
  → authorized download by attachment ID + security event
```

- Имя файла нормализуется для отображения; storage key генерируется сервером.
- Content-Type клиента не является доказательством. SVG/HTML остаются attachment/download как в текущем `file_response`; `nosniff`, CSP и private no-store сохраняются.
- Размеры текущих лимитов не увеличивать без отдельного решения: документы 50 МБ, медиа 300 МБ, импорт 30 МБ. Support — до 50 МБ на файл.
- Импорт XLSX/DOCX проверяется до парсинга; parser limits защищают от zip bombs, глубокой вложенности и чрезмерного времени.

### 8.2 ClamAV deployment

- `clamd` в отдельном контейнере/private network, без публичного порта;
- pinned image/version и автоматическое обновление signatures с мониторингом freshness;
- лимиты CPU/RAM/file size/archive recursion/timeouts;
- health/readiness отражает реальную доступность daemon;
- новые uploads при scanner down получают `error`/503 и не становятся доступными;
- на 4 ГБ RAM провести нагрузочный тест backend+PostgreSQL+ClamAV. При OOM/деградации вынести scanning на isolated worker, уменьшить concurrency; не выставлять clean без сканирования.

### 8.3 Старые файлы и recovery

Существующие attachments маркируются `legacy_unscanned`, остаются доступны по старым правам и скачиваются с audit. Их можно постепенно сканировать отдельной командой; найденный infected изолируется по runbook без удаления доказательств в открытом виде. Recovery copy не сканируется автоматически в общий production.

## 9. Приватные ссылки и S3

Текущий S3 `generate_presigned_url(... ExpiresIn=3600)` изменить:

- пользовательские DTO не сохраняют и не возвращают постоянный presigned URL;
- `Attachment.storage_url` legacy используется только как внутренний reference после инвентаризации; нельзя считать его безопасным API;
- download endpoint принимает attachment ID, повторно проверяет actor/entity/deal/legal/cost/support visibility и scan status;
- затем либо stream через backend, либо выдаёт presigned GET максимум на 300 секунд с `response-content-disposition=attachment` для небезопасных типов;
- URL не журналируется, не включается в AI/support text и не имеет публичного постоянного характера;
- revoked/offboarded user не может получить новый URL; уже выданный короткий URL технически может жить до истечения — именно поэтому срок 5 минут и приватный bucket обязательны;
- анонимные permanent public routes запрещены.

## 10. Реальные данные в test/recovery/AI

### 10.1 Классификация сред

- `APP_ENV=production`, `DATA_CLASSIFICATION=production`;
- `APP_ENV=test|development`, `DATA_CLASSIFICATION=synthetic`;
- `APP_ENV=recovery`, `DATA_CLASSIFICATION=recovery` — единственное исключение для восстановленного production dump.

Backend на старте отклоняет небезопасные комбинации, например synthetic-only test с production DSN, recovery с включёнными mail/LLM/WeCom. Не полагаться только на имя БД.

### 10.2 Recovery

Отдельная ВМ/сеть/credentials, без production S3 writer и публичного доступа. Отключены deploy timers, external mail/messenger/LLM, webhooks и scheduled business jobs. Recovery не используется для обычной разработки и удаляется после drill.

### 10.3 ИИ

Не вставлять production dump, секреты, закрытые документы или чужие персональные данные в Claude prompt. Внутри CRM AI provider включается владельцем отдельно; CRM tools отправляют только минимальный разрешённый контекст после server-side filtering. General mode по умолчанию не включает текущую страницу и CRM history.

## 11. Security test matrix

Обязательны автоматические тесты:

- JWT без/с чужим/отозванным/expired `sid`;
- logout делает повторный cookie недействительным;
- offboarding мгновенно блокирует API и старый токен;
- изменение пароля/pv отзывает прежние входы;
- MFA required не даёт обойти challenge прямым API;
- recovery code одноразовый;
- последний security admin/self-offboard защищены;
- override expiry и delegations завершены;
- чужой support/security/AI объект — 404;
- неавторизованный export не раскрывает данные и создаёт denied event;
- infected/pending/error file не скачивается;
- legacy_unscanned доступен только по старым правам;
- presign <=300 секунд и выдаётся после auth;
- alert не приходит нарушителю без security права;
- события не содержат известные synthetic secret canaries;
- recovery startup падает при включённых внешних каналах.

## 12. Rollout без потери доступа

1. Миграции и code deploy в optional MFA; sessions создаются для новых входов.
2. Владелец и резервный security admin настраивают TOTP/recovery.
3. Короткий migration window старых sessions, затем принудительный перевыпуск.
4. Проверить все auth methods и revoke.
5. Включить required MFA после явного подтверждения.
6. Включить scanner сначала на synthetic/quarantine и нагрузочный тест; затем new uploads fail-closed.
7. Постепенно включить журнал всех exports/downloads, проверить объём и отсутствие sensitive payload.
8. Отдельно запланировать quarterly review.
