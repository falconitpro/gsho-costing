# Приёмочные тесты

## 1. Правила приёмки

Для каждого теста фиксировать: ID, дату, commit, ветку/PR, окружение, команду или ручные шаги, фактический результат, ссылку на sanitized evidence. Все данные синтетические. Production restore evidence — только counts/hashes/status без содержимого.

Статусы: `PASS`, `FAIL`, `BLOCKED` с причиной. `NOT RUN` не равен PASS. Нельзя закрывать этап с FAIL/BLOCKED обязательных тестов.

Общий regression:

- чистая PostgreSQL 16, существующие и новые migrations;
- backend tests, frontend typecheck/build, CI;
- существующие deals/legal/parts/finance/workplace flows;
- роли: ЗГД, admin, менеджер, наблюдатель, пользователь без финансовых прав, support READ/EDIT, security admin/audit;
- 1440/1280/768/390 px, Chrome/Chromium минимум; Firefox/Safari по доступности не заявлять без запуска.

## 2. Миграции

### MIG-01 — чистая схема

Применить существующие change set’ы и новые в зафиксированном порядке на пустую DB. Ожидание: все tables/columns/indexes соответствуют моделям, backend стартует.

### MIG-02 — идемпотентность

Повторно применить каждый новый SQL. Ожидание: нет duplicate constraint/index errors, существующие строки не изменились смыслово, counts не удвоились.

### MIG-03 — существующие данные

До migration вставить synthetic users/tasks/attachments/overrides. После: значения сохранены, новые defaults корректны, старые attachments `legacy_unscanned`, рабочие workplace/finance responses совместимы.

### MIG-04 — rollback/transaction

В rehearsal создать контролируемую ошибку в середине копии change set. Ожидание: транзакционные изменения откатились, нет половины схемы. Не выполнять destructive rollback на production.

### MIG-05 — ORM/SQL parity

Сравнить metadata models и information_schema: типы, nullable, defaults, FK, unique, indexes. Не полагаться на `create_all` в production.

### MIG-06 — backup перед apply

Проверить deploy dry-run: при `BACKUP_REQUIRED=true` failed pre-deploy останавливает обновление до build/migration; при успехе snapshot реально виден в Yandex/restic.

## 3. Backup и восстановление

### BKP-01 — расписание

Проверить `systemd-analyze calendar` и `list-timers`: 19:00 Europe/Moscow, ежедневно, `Persistent=true`. Смоделировать пропущенный запуск после reboot.

### BKP-02 — содержимое

Manual run на synthetic system: custom dump читается `pg_restore --list`, файлы включены, manifest имеет reason/commit/schema/provider/sizes/SHA-256/snapshot, staging удалён.

### BKP-03 — клиентское шифрование

Скачанный из бакета объект не даёт открытого SQL/файлов без RESTIC_PASSWORD. Неверный пароль не восстанавливает данные. Секреты не попали в logs/status.

### BKP-04 — отказ S3/сети

Run завершается failed/nonzero, прежний snapshot не удалён, status sanitized failed, app alert создаётся при доступной CRM. Нет ложного success.

### BKP-05 — диск/стaging

При нехватке места run failed, partial artifacts не считаются копией, старые снапшоты сохранены, staging cleanup безопасен.

### BKP-06 — concurrency

Два запуска одновременно: один выполняется, второй lock/already_running; нет двух prune и повреждения status.

### BKP-07 — retention

На synthetic restic repo с датами snapshots проверить 90 daily/12 monthly; monthly не теряется преждевременно. Lifecycle не удаляет нужные текущие объекты.

### BKP-08 — права SA

Restore read-only не может write/delete; backup не меняет IAM/ACL/policy и не видит чужие бакеты; anonymous denied. Широкие inherited roles отсутствуют.

### BKP-09 — stale status

Отсутствие успеха >26 часов показывает stale и alert. При недоступной БД host status сохраняется; UI не показывает устаревший success как свежий.

### BKP-10 — полный restore

На чистой recovery-ВМ восстановить БД/файлы, проверить hashes/counts/schema/health/read-only smoke. Внешние каналы отключены. Два последовательных daily успешны до этого.

### BKP-11 — итоговый restore на актуальной схеме

После security/support/AI/briefing migrations повторить restore и login/read smoke. Старый restore drill не засчитывать автоматически для новой схемы.

### BKP-12 — отключение Timeweb

До подтверждения старый service работает. После checklist и явного owner approval: service удалён без `down -v`, provider backup отключён вручную, рабочие pgdata/storage не тронуты, новый timer работает после reboot.

## 4. Аутентификация, MFA, пароли

### SEC-01 — logout revoke

Войти с двух браузеров, logout в одном. Повтор прежнего cookie → 401, вторая session продолжает работать.

### SEC-02 — revoke others

«Все, кроме текущей» → остальные sid немедленно 401, текущая работает, событие создано.

### SEC-03 — admin revoke

Security admin завершает чужую session; обычный admin без права не может. Token/cookie не отображаются в API/UI/log.

### SEC-04 — idle/absolute

Time-travel/unit tests: idle expiry, absolute expiry, remember limits, last_seen update не чаще 60 секунд.

### SEC-05 — MFA challenge

После пароля с включённым MFA нет полноценного CRM доступа до verify. Прямой API request с mfa_pending отклонён. Expiry/attempts работают.

### SEC-06 — recovery code

Code работает один раз, повтор отклонён, regenerate отзывает старые codes. DB содержит только hashes.

### SEC-07 — required rollout

Пользователь без MFA получает только me/setup/logout. После setup полный доступ. OIDC без подтверждённого MFA также проходит local TOTP.

### SEC-08 — MFA reset

Требует права и step-up, отзывает sessions, создаёт alert/app notice. Нельзя оставить систему без последнего security admin.

### SEC-09 — парольная политика

11 символов/common/login-only/no digit rejected; 12–128 valid; последние 5 нельзя повторить; старый PBKDF2 login работает и rehash прозрачен.

### SEC-10 — temporary password

Admin reset отзывает sessions, до смены доступны только необходимые routes. Новый пароль не появляется в logs/audit.

### SEC-11 — benchmark

На 2 vCPU измерить login p50/p95 и CPU до/после стоимости hash. Нет массового timeout/DoS. Результат записан.

## 5. Offboarding и права

### OFF-01 — атомарное отключение

Пользователь имеет sessions, overrides, delegations, tasks, support/finance questions. После offboard: old cookie 401, active=false, sessions/challenges revoked, delegations/overrides завершены, tasks flagged, tickets unassigned, история сохранена.

### OFF-02 — обход через старые endpoints

Каждый существующий admin/team update с `is_active=false` вызывает ту же операцию. Нет пути частичного disable.

### OFF-03 — safeguards

Self-offboard и last security admin rejected. Concurrent double offboard не даёт частичного состояния/дублей.

### OFF-04 — rollback

Искусственная ошибка на связанном шаге откатывает активность, sessions и overrides; владелец видит failed, не success.

### OFF-05 — reactivation

Старые sessions/overrides не воскресают; требуется новый вход/MFA и пересмотр прав.

### REV-01 — кампания

Создан snapshot всех нужных прав, reminders 14/7/1, overdue alert. Нет secrets/tokens.

### REV-02 — self-approval

Reviewer не может в одиночку утвердить собственное повышение. Второй reviewer и audit обязательны.

### REV-03 — решения

Keep не меняет права; change выполняет реальные изменения и diff; disable вызывает offboard. Completion не скрывает pending items.

## 6. Скачивания, алерты и файлы

### AUD-01 — успешный/запрещённый export

События содержат actor/entity/format/rows/result/request ID, но не rows contents/secrets/signed query. Denied не раскрывает данные.

### AUD-02 — все routes

Пройти инвентаризированный список file/export endpoints. Для каждого проверить auth+scan+audit; ни один bypass не остаётся.

### AUD-03 — thresholds

Синтетические 5/6 exports и 20/21 downloads проверяют границу, dedup count/last_seen, получатели только security_audit/admin. Нарушитель без права alert не получает.

### AUD-04 — изменения прав

Role/override/MFA reset/offboard создают high/critical alert и immutable event без полного sensitive payload.

### FILE-01 — clean upload

Clean файл проходит quarantine → clean → promote, скачивается авторизованным пользователем с текущими safe headers.

### FILE-02 — infected

Стандартная антивирусная тестовая сигнатура вызывает infected, файл недоступен, quarantine обработан, metadata/hash сохранены. Не использовать реальный malware.

### FILE-03 — scanner down/error/timeout

Новый файл не доступен и не парсится импортом; пользователь видит 503/error. После recovery можно retry; нет автоматического clean.

### FILE-04 — legacy

Старый файл legacy_unscanned доступен по прежним правам, denied пользователь по-прежнему не получает. Скачивание журналируется.

### FILE-05 — support attachment

Reporter и support admin имеют доступ по правилам; другой сотрудник/обычный admin — 404. Scan gate действует.

### FILE-06 — S3

Presign <=300 секунд, создаётся после object auth, не сохраняется в DTO/логах как постоянный. Bucket anonymous denied.

### FILE-07 — активный контент/архивы

SVG/HTML не исполняются inline, nosniff/CSP/private no-store сохранены. Archive bomb/depth/oversize отклонены в пределах лимитов.

### FILE-08 — ресурсы

При параллельных uploads и backup нет OOM/недопустимой деградации на 2 vCPU/4 ГБ. При недостатке ресурсов isolated worker проверен отдельно.

## 7. Внутренняя поддержка

### SUP-01 — создание

Все обязательные поля/limits, metadata просмотр, ticket номер формата, in-app notice. Почта/SMTP mock не вызван.

### SUP-02 — concurrency/idempotency

20 параллельных creations: unique numbers; повтор одного idempotency key не создаёт дубль.

### SUP-03 — ownership

Reporter видит своё; другой сотрудник и admin без support_admin — 404 на list item/card/attachment; counters не раскрывают чужие темы.

### SUP-04 — READ vs EDIT

READ видит очередь, но message/assign/priority/transition rejected. EDIT выполняет и создаёт system/audit events.

### SUP-05 — state machine

new→in_progress→waiting→reply→resolved→reopen→closed; closed immutable; invalid transition 409/400 без побочных уведомлений.

### SUP-06 — уведомления

Только `channel="app"`, правильные recipients/routes/dedup; email/WeCom не вызываются.

### SUP-07 — offboarding

Assigned specialist снимается, ticket не закрыт, queue alert создан. Reporter offboard не удаляет историю.

### SUP-08 — XSS/ошибки

Script-like текст отображается безопасно; server error не теряет draft; correlation ID показан без stack.

## 8. Сводка

### BRF-01 — приоритет и дедуп

Просроченное выше today/tomorrow/3 days; одна задача не повторяется из task+notification+focus; 3–5 элементов.

### BRF-02 — факты

Каждый title/due/amount/source/url соответствует исходному экрану. Нет реального совещания — нет фразы о нём.

### BRF-03 — финансовая parity

Остаток/дата/валюта совпадают с finance service для той же роли. RUB/CNY/USD не суммируются. Data quality warnings сохранены.

### BRF-04 — visibility

Роли/overrides/acting_for/legal/finance/cost/factory checks не раскрывают закрытые поля и counts.

### BRF-05 — actions

Pin/snooze/hide/reset работают только на своего candidate; срок источника не меняется; changed signature возвращает элемент.

### BRF-06 — выполнение/обновление

Завершение задачи/payment/ticket убирает/обновляет элемент после refresh. generated_at фактический.

### BRF-07 — fallback

LLM off/timeout не меняет блок; один источник error не ломает workplace и не показывается как нулевой.

### BRF-08 — layout

Старая user layout сохранена, briefing добавлен один раз после focus по умолчанию; настройки reorder работают.

## 9. ИИ

### AI-01 — owner/IDOR

Чужие conversations/messages/feedback 404; security/support/admin roles не читают содержимое без владельца.

### AI-02 — tools auth matrix

Каждый tool тестируется со всеми ролями, deal restrictions, finance Visibility, acting_for и overrides. Provider payload не содержит закрытые canary fields.

### AI-03 — arbitrary action

Попытки arbitrary SQL/tool/user_id/file path/write commands отклонены. Нет DB session/shell/env в model context.

### AI-04 — источники

Unknown/модельный URL/ID удаляется; citations только из tool results; deep links повторно проверяют права.

### AI-05 — debt/price

Финансовый ответ совпадает с существующими services, разделение валют/confirmed/provisional/as_of. Нет данных — не ноль.

### AI-06 — provider none/failure

Help и deterministic tools работают; general честно disabled/fallback; timeout/invalid output не выдаёт выдумку.

### AI-07 — quota/concurrency

Minute/daily limits нельзя обойти parallel requests; retry одного logical request не расходует лишнюю quota ошибочно.

### AI-08 — retention/delete

История скрыта/удалена по политике, sanitized audit остаётся без содержимого. Secrets canaries отсутствуют.

### AI-09 — общий режим

CRM page/history/tools не отправляются в general provider payload.

## 10. Browser end-to-end

Для каждого этапа выполнить реальные клики:

1. Header Support → создать ticket → attach clean file → specialist reply → reopen/close.
2. Header Assistant → CRM question → source link → help question → history/delete.
3. Workplace briefing → open source → pin/snooze/hide/reset → complete source → refresh.
4. Settings Security → MFA setup/recovery → second browser login → sessions revoke.
5. Security admin → offboard synthetic user → old browser loses access → tasks/tickets queues.
6. Alerts → threshold event → ack/resolve.
7. Backup status → success/failure/stale; manual CTA либо runbook.
8. File upload states clean/pending/infected/error, download denied/clean.

На каждой ширине 1440/1280/768/390:

- нет горизонтального overflow основной страницы;
- focus/keyboard/Esc работают;
- console без ошибок, network без unexpected 4xx/5xx;
- loading завершается, errors видимы, drafts не теряются;
- нет мёртвых кнопок и fake success;
- screenshots synthetic, без секретов/реальных данных.

## 11. Финальный критерий

Все обязательные тесты выбранных блоков PASS, production-only проверки честно отмечены как выполненные владельцем либо ожидающие его действий. PR содержит доказательства, журналы обновлены. Restore gate и Timeweb approval не могут быть заменены unit tests.
