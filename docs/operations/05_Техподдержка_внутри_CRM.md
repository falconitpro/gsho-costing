# Техподдержка внутри CRM — без почты

## 1. Результат

Сотрудник из любого раздела CRM может открыть «Поддержку», описать ошибку или вопрос, приложить файл и следить за ответом внутри системы. Владелец или назначенный специалист обрабатывает очередь. Обращения и вложения хранятся в CRM с разграничением доступа.

**Не реализовывать:** email-уведомления, SMTP, отдельный почтовый ящик, DNS, Яндекс 360, исходящие письма и автоматическое создание писем. Существующие каналы пользователя не должны незаметно активироваться общим `notify()`.

## 2. Роли и видимость

| Действие | Активный сотрудник | `support_admin=READ` | `support_admin=EDIT` |
|---|---|---|---|
| Создать обращение | да | да | да |
| Видеть свои обращения | да | да | да |
| Отвечать в своём | да | да | да |
| Закрыть своё решённое / вернуть в работу | да | да | да |
| Видеть общую очередь | нет | да | да |
| Читать чужие тексты/вложения | нет | да | да |
| Назначать, менять приоритет/статус | нет | нет | да |
| Отвечать как специалист | нет | нет | да |
| Управлять правом поддержки | только `access_admin` по существующему контуру | нет | нет |

- По умолчанию `support_admin=EDIT` только у ЗГД, остальные роли 0; владелец может выдать дополнительные права через существующую матрицу.
- Обычная роль `admin`, `security_audit`, `assistant_admin` и `backup_status` не раскрывают содержимое обращений.
- Чужой ticket/message/attachment — 404. Список не раскрывает число и темы чужих обращений через counters/search suggestions.
- Support admin не получает дополнительных прав на сделки, финансы и AI conversations. Если в ticket приложена ссылка на сделку, доступ к ней проверяется отдельно.

## 3. Создание обращения

### 3.1 Входные точки

- шапка CRM: иконка/кнопка «Поддержка» с числом непрочитанных обновлений в своих тикетах;
- `/support` — «Мои обращения»;
- рабочее место — компактная кнопка «Сообщить о проблеме»;
- error state страницы — ссылка «Сообщить в поддержку», автоматически подставляющая route и correlation ID. Не отправлять stack trace, tokens или весь API response автоматически.

### 3.2 Поля формы

Обязательные:

- категория: `Ошибка`, `Вопрос по работе`, `Доступ`, `Предложение`;
- тема: 5–200 символов;
- описание: 10–8000 символов. Для ошибки placeholder: что делали, что ожидали, что произошло, время;
- запрошенная срочность: обычная/высокая/критичная. Критичная — система недоступна или работа остановлена; подсказка предотвращает выбор критичной для любого вопроса.

Автоматически, с возможностью просмотра:

- текущий frontend route без sensitive query params;
- app version/git commit;
- correlation ID последней ошибки, если есть;
- browser family/version, OS family, viewport; без полного fingerprint;
- локальное время пользователя и timezone.

Вложения: до 5, каждый до 50 МБ. Проходят общий quarantine/scan/download audit. Подпись у dropzone: «Не прикладывайте пароли, ключи, токены и документы, не нужные для диагностики». Файл доступен только после `clean`.

### 3.3 Сохранение

- Один submit не создаёт дубль: disable button + client request key + серверная идемпотентность по `(reporter_id,idempotency_key)` за короткое окно.
- Тикет, первое сообщение, связь вложений и номер создаются транзакционно; файлы предварительно проходят scan через upload session.
- Номер `SUP-YYYY-NNNN` формируется через row lock sequence по году; одновременные создания не дают одинаковый номер.
- `status=new`, `priority` первоначально соответствует requested urgency, но специалист может изменить отдельно.
- Автор видит подтверждение «Обращение SUP-… создано. Ответ появится здесь и в уведомлениях CRM» — без обещания письма.

## 4. Жизненный цикл

```text
new → in_progress → waiting_reporter → in_progress
  │        │              │
  │        └──────────────┴→ resolved → closed
  │                              │
  └──────────────────────────────┴─ возврат автора → in_progress
```

Правила:

- Первый ответ специалиста заполняет `first_response_at` один раз; при необходимости переводит `new → in_progress`.
- `waiting_reporter`: специалист обязан указать, какая информация нужна. Ответ автора возвращает `in_progress` и уведомляет специалиста.
- `resolved`: специалист добавляет сообщение с решением/обходом/ссылкой на версию. Автор может закрыть или нажать «Проблема осталась».
- `closed`: финальное состояние; сообщения/attachments запрещены. Новый случай — новый ticket, можно указать прежний номер как текстовую ссылку.
- Автор не может сам закрыть активный спорный тикет без подтверждения? Разрешить закрытие своего тикета в любом не closed статусе с подтверждением «Обращение будет закрыто»; это не удаление.
- Системные переходы offboarding/assignee меняют только назначение, не закрывают проблему.
- Повторный одинаковый status update идемпотентен, не создаёт дубли system messages/notifications.

## 5. Сообщения и вложения

- Хронология oldest → newest, новые сообщения подгружаются без потери введённого текста.
- `kind=user|specialist|system`; system events не принимаются от клиента и визуально отделены.
- Сообщения нельзя редактировать/удалять. Опечатка — новое сообщение.
- Тело хранится как текст; frontend не вставляет его через опасный HTML. Markdown либо plain text по единой безопасной политике; scripts/HTML не исполняются.
- Вложение связывается с тикетом и необязательным сообщением. Доступ проверяется через родительский тикет, затем scan status, затем выдаётся короткий protected download.
- Удаление автора из активных сотрудников не удаляет историю. Отображается «Сотрудник отключён».

## 6. Очередь специалиста

`/support/admin`:

- KPI: новые, без первого ответа, ждут автора, просрочены, решены за период;
- фильтры: статус, категория, приоритет, назначенный, период;
- поиск: номер, тема; поиск по содержимому только для authorised support admin и с ограничением;
- сортировка: сначала critical/high и просроченные, затем oldest unread;
- список с номером, темой, автором, временем, статусом, назначенным и последним ответом;
- массовые действия не обязательны в первом срезе; не добавлять неработающие checkboxes.

Карточка специалиста дополнительно содержит:

- выбор assignee среди активных `support_admin`;
- внутренний приоритет;
- ответ/статус;
- технические метаданные запроса;
- audit/system history;
- безопасный preview attachments.

Не добавлять «внутренние заметки», если модель не разграничивает их от сообщений автору. Если нужны — отдельный `kind=internal` с жёсткой фильтрацией DTO и тестом, но в первый срез не включать.

## 7. Только in-app уведомления

Создать `services/support_notifications.py` или аналогичный helper, который пишет **только** `NotificationLog(channel="app")` и обновляет unread count. Не вызывать общий `notify()` без явного channel adapter, поскольку он может учитывать email/WeCom.

События:

- `support_ticket_created` — support admins;
- `support_ticket_assigned` — новому специалисту;
- `support_message_reporter` — assignee/queue, без дублей всем при каждом сообщении по принятой политике;
- `support_message_specialist` — автору;
- `support_waiting_reporter` — автору;
- `support_resolved` — автору;
- `support_reopened` — assignee/queue;
- `support_unassigned_offboard` — support admins.

Добавить titles в существующий `EVENT_TITLES`. Payload: ticket ID, номер, безопасная тема, route `/support/:id` либо `/support/admin?ticket=:id`. Тело сообщения и attachment payload в notification не дублировать.

Дедупликация: одно событие на commit ID. Повторная доставка job не создаёт десяток одинаковых уведомлений. Read state использует текущий notifications API.

## 8. Внутренние SLA

SLA помогает владельцу, не отправляет внешние сообщения:

| Запрошенная срочность | Первый ответ — ориентир |
|---|---|
| critical | 4 рабочих часа |
| high | 1 рабочий день |
| normal | 2 рабочих дня |

- Рабочий календарь/часы задаются конфигурацией, timezone Europe/Moscow по умолчанию; не выдумывать праздничный календарь без источника.
- При отсутствии календаря честно считать календарные сроки и обозначить это.
- Просрочка — badge и элемент сводки специалиста с правом поддержки.
- Запрошенная срочность не равна фактическому приоритету. Смена приоритета логируется.

## 9. Интеграция с другими блоками

### Offboarding

Если увольняемый — assignee, тикет остаётся открытым, `assignee_id=null`, создаётся system event и app alert support admins. Если увольняемый — reporter, тикет остаётся в истории; специалист может решить/закрыть, ответ не открывает пользователю доступ.

### Ежедневная сводка

- автору: ответ специалиста/ожидание его данных;
- специалисту: новые и просроченные тикеты, назначенные ему либо общая очередь по праву;
- без support admin пользователь не видит чужие тикеты и глобальные SLA counters.

### ИИ

Help tool может объяснить, как создать обращение. ИИ не читает чужие tickets. Чтение собственного ticket возможно только отдельным будущим allowlist tool; в первом срезе не требуется. Кнопка «Создать тикет» из drawer должна вести на настоящую форму, а не просить модель выполнить запись.

### Security

Создание, denied access, скачивание вложений, смена назначения и статусов журналируются с разными уровнями детализации. `security_audit` видит факт события, но не текст тикета.

## 10. API-результат и ошибки

- `POST /api/support/tickets` — 201, номер и ticket DTO;
- `GET /api/support/tickets` — только свои, pagination;
- `GET /api/support/tickets/{id}` — reporter либо support admin;
- `POST /api/support/tickets/{id}/messages` — разрешённый участник, запрещено в closed;
- `POST /api/support/tickets/{id}/transition` — whitelist переходов по роли;
- `POST /api/support/tickets/{id}/assign` — support_admin EDIT;
- `GET /api/support/admin/tickets` — support_admin READ;
- attachments используют общий secure upload/download контур.

Ошибки: 400 validation, 401 no session, 403 известный объект но недостаточно действия, 404 чужой/несуществующий, 409 недопустимый переход/конфликт версии, 413 file limit, 503 scanner temporarily unavailable. Не возвращать SQL/stack trace.

## 11. Приёмочные сценарии

1. Сотрудник создаёт тикет с двумя clean files, получает уникальный номер и видит только его.
2. Одновременно созданные 20 тикетов имеют разные номера без дыр, приводящих к конфликту; при serialization retry нет дублей.
3. Другой сотрудник и обычный admin без support_admin получают 404 на ticket и attachment.
4. Support READ видит очередь, но не может ответить/назначить.
5. Support EDIT отвечает, статус и timestamps меняются, автор получает только app notification; mail adapter mock не вызывается.
6. Waiting → ответ автора → in_progress; resolved → reopen; closed → сообщение запрещено.
7. Infected file не появляется в тикете как доступный; scanner error не даёт bypass.
8. Offboarded assignee снимается; тикет не потерян.
9. Скрытая XSS-строка в теме/сообщении отображается как текст.
10. Мобильная форма 390 px позволяет создать тикет, ответить и открыть файл без горизонтального переполнения.
