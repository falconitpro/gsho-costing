## D-005 — Два Yandex SA и роли

- Решение: backup SA `storage.editor` только на выделенный bucket; restore SA `storage.viewer` только на него.
- Причина: restic требует read/list/lock/delete/prune; `storage.uploader` недостаточен, `storage.admin` избыточен.
- Дополнительно: проверить отсутствие широких inherited roles на каталог/облако.
- Статус: проектное решение.

## D-006 — Object Lock не входит в первичный rollout

- Решение: versioning включить; Object Lock и сложные lifecycle правила не включать автоматически.
- Причина: lock может конфликтовать с `restic forget --prune` и препятствовать удалению объектов до срока.
- Будущий hardening: отдельный repository/bucket test, согласование сроков и стоимости.
- Статус: зафиксировано.

## D-007 — Gate отключения Timeweb

- Решение: старый backup работает, пока не будут manual + две последовательные daily + check + полное восстановление на recovery-ВМ + явное подтверждение владельца.
- Только затем: удалить Compose service, владелец вручную отключить provider backups, контролируемая очистка старых архивов.
- Запрещено: `docker compose down -v`, автоматическое удаление volumes.
- Статус: обязательный gate.

## D-008 — Наблюдаемость backup

- Решение: атомарный host `last-run.json` + sanitized `BackupRun`, in-app failed/stale alerts.
- Ограничение: при полном падении сервера in-app alert недоступен; внешний heartbeat рекомендован, но не заявлен реализованным.
- Статус: проектное решение.

## D-009 — Server-side sessions

- Решение: JWT получает `sid`, каждая CRM-сессия имеет AuthSession с idle/absolute expiry и revoke; logout/revoke/offboard проверяются сервером.
- Совместимость: короткий migration window, затем old stateless tokens отклоняются; постоянного bypass нет.
- Статус: проектное решение.

## D-010 — MFA и пароли

- Решение: TOTP, зашифрованный secret, recovery hashes, mfa_pending 5 минут, optional → required после подтверждения.
- Пароли: 12–128, буквы+цифры, denylist, history 5, temporary must-change, старые hashes поддерживаются.
- Hash cost повышается после benchmark; обязательная смена каждые 90 дней не вводится.
- OIDC MFA принимается только при подтверждённых amr/acr/политике.
- Статус: проектное решение.

## D-028 — Политика хранения: одна группа на хост, постоянный путь staging

- Дата: 11.11.2026.
- Решение: `restic forget --host gsho-prod --tag gsho --group-by host --keep-daily 90 --keep-monthly 12 --prune`. Staging — постоянный каталог `<BACKUP_STAGING_DIR>/gsho-backup` под `flock`, а не `mktemp -d`.
- Причина: по умолчанию restic применяет политику отдельно к каждой группе «хост + пути». При случайном пути staging каждый снимок попадал бы в свою группу, и `--keep-daily 90` ничего бы не удалял. Тест `test_retention_daily_and_monthly` на синтетических снимках с датами это выявил и закрепил исправление. Постоянный путь под блокировкой даёт и родительский снимок для дедупликации.
- Подтверждение владельца: не требуется.
- Статус: действует.

## D-031 — После #140/#141 CI снова красный: две причины

- Дата: 11.11.2026, 01:03 МСК.
- Контекст: merge #141 (`c1faa76`) и #140 (`8340894`) — backend failure в обоих.

- Подтверждение владельца: в рамках разрешения «чинить красный CI» (11.11.2026).
- Проверки: весь backend на чистой PG16 — 243 passed / 0 failed / 1 skipped.

## D-049 — Проверка загрузок: единая прослойка, синхронно, fail-closed, образец не хранится

- Дата: 11.11.2026.
- Решение:
  - Все multipart-загрузки к API проходят ASGI-прослойку `core/upload_gate.py`: тело запроса сохраняется во временный файл (вне хранилища, случайное имя — это и есть карантин), файлы из него проверяются, только потом тело отдаётся обработчику. Проверка FastAPI-маршрутов «обёрткой» не годится: FastAPI 0.162 вызывает свои копии маршрутов (выяснено в тестах). Новый маршрут с загрузкой проходит проверку без доработки (тест добавляет такой маршрут).
  - Порядок: вход (без входа файл не проверяется, отвечает обработчик) → zip-бомбы и вложенность архивов (`.zip`, `.xlsx`, `.docx`…; всегда, даже без антивируса; до разбора импортом) → clamd по протоколу INSTREAM (путь на диске scanner не получает) → обработчик.
  - Проверка синхронная: статуса `pending`, видимого сотруднику, нет. Чистый → файл сохраняется как раньше, `attachments.scan_status = clean`. Заражён → 422, файл не сохраняется, **образец не хранится** (только SHA-256, размер, имя сигнатуры, кто и куда загружал), событие и **критическое** предупреждение. Превышены лимиты проверки (`Heuristics.Limits.Exceeded`) → 422 «превышены ограничения». Антивирус недоступен, таймаут → 503, файл не принят, предупреждение «Проверка файлов недоступна»; автоматического «чисто» нет.
  - `FILE_SCAN=off` (по умолчанию, пока владелец не включил clamd): файлы принимаются, статус `legacy_unscanned` («не проверялся»). Защита от zip-бомб работает и в этом режиме. При `APP_ENV=prod` режим off запрещён (D-050).
  - Старые файлы — `legacy_unscanned`, доступны по прежним правам, скачивание в журнале (FILE-04). `scripts/scan_storage.py` проверяет их: заражённый переносится в `QUARANTINE_DIR` (вне хранилища, 0600, случайное имя), перестаёт выдаваться (410), критическое предупреждение. Ничего не удаляется.
  - ClamAV — свой образ на базе `python:3.12-slim` (тот же, что у backend; Docker Hub не нужен), compose-профиль `scanner`, без публичного порта, предел 2 ГБ, `ConcurrentDatabaseReload no` (ВМ 3,8 ГБ без swap, проверено владельцем 11.11). Базы — с зеркал `packages.microsoft.com/clamav` и `clamav-mirror.ru`: `database.clamav.net` отвечает 403 для российских адресов (проверено на стенде). Подпись баз проверяет freshclam.
  - Ежечасно: clamd не отвечает → «Проверка файлов недоступна»; базы старше 48 ч → «Антивирусные базы устарели».
- Статус: действует. Включение на стенде — владелец по `deploy/clamav/install.md`.

## D-052 — SLA поддержки в календарных часах; X-Request-ID; фоновый цикл не запускается в тестах

Автор видит, что именно будет передано, и может отключить технические данные. Из адреса страницы убираются параметры вида token, code, key.

  - **ИИ-переписывание** (`BRIEFING_AI_REWRITE`) не реализовано — провайдера ИИ пока нет (этап 6); сводка полностью детерминированная.

## D-058 — Перенос со стенда: база целиком, без паролей и служебных данных (решение владельца)

- Дата: 11.11.2026. Основание: сводка `scripts.db_inventory` со стенда (17 сделок, 2 заявки, 9 сотрудников, 25 672 запчасти, база 34 МБ).

- Способ: копия стенда из Yandex Object Storage восстанавливается в пустую базу рабочего сервера (`deploy/production/transfer-from-stand.sh`), затем `scripts.prod_init adopt`. Выборочной сборки по таблицам нет: переносится всё, связи между записями не рвутся. Это же служит проверкой восстановления.
- `adopt` сбрасывает: пароли и историю паролей, коды из приложения и резервные коды, сессии, уведомления, диалоги и счётчики Помощника, состояния сводки, пересмотр прав, журнал копий стенда. Не трогает: сделки, файлы, справочники, сотрудников и права, `audit_log`, журнал безопасности. В `audit_log` добавляется запись `adopt_from_stand`.
- Защита: скрипт переноса работает только при незапущенной CRM и пустой базе; при несовпадении контрольной суммы база не трогается. `adopt` отказывается работать на базе с отметкой `production` — после первого запуска рабочей системы сбросить всем пароли этой командой нельзя.
- Курсы ЦБ: `scripts.prod_init fx` заменяет курсы `cbr` загруженными с cbr.ru. Причина: первые курсы на стенде были выдуманными (демо-скрипт), а дозагрузка истории пропускает даты, которые уже есть, — выдуманные значения могли остаться. Валюта заменяется только при успешной загрузке; ручные курсы не затрагиваются. Проверить, остались ли выдуманные курсы на стенде, из песочницы нельзя.
- Ключ чтения копий стенда кладётся на рабочий сервер только на время переноса и удаляется сразу после сверки.
- Следствие: данные стенда с момента переноса считаются рабочими. После переноса стенд остаётся для проверок обновлений; новые настоящие данные вносятся только на рабочем сервере.
- Статус: действует.
