# Ежедневная сводка-подсказка

## 1. Назначение

На рабочем месте пользователь видит короткий персональный список: что требует его действия, почему это важно и что сделать сначала. Сводка не является генеративным прогнозом и не создаёт новые задачи. Она строится из фактических данных CRM и **работает без ИИ**.

## 2. Размещение и обновление

- Новый block key `briefing`, название «Ваши приоритеты».
- Добавить в существующие `BLOCKS`, `ROLE_BLOCKS` и workplace layout. В `WorkplacePage.tsx` — тип DTO, `estimate`, renderer и block в центральной группе `WIDE`, после `focus` по умолчанию.
- Сохранённые `User.prefs["workplace"]` не сбрасывать: при отсутствии briefing в старой раскладке добавить его один раз в безопасную позицию, не перезаписывая остальные настройки.
- GET `/api/workplace` вычисляет свежий block; отдельный `GET /api/briefing` допустим для actions/refresh, но не должен давать другой набор фактов при одинаковом времени.
- После завершения задачи, ответа на обращение, обновления approval/payment frontend повторно загружает workplace либо вызывает refresh briefing.
- Показывать фактический `generated_at`, кнопку «Обновить» и состояние ошибки источника. Не писать «обновлено только что» при cached/stale данных.

## 3. Источники и допуск

| Источник | Условие появления | Deep link |
|---|---|---|
| `Task` | assignee текущий пользователь/разрешённый acting_for, не выполнена, due просрочен/близок | существующая задача/сделка |
| Workplace `focus/attention` | уже отфильтрованный критичный элемент | URL из DTO |
| Этапы исполнения | пользователь ответственен и есть реальный срок/блокировка | этап/сделка |
| Approvals | ожидает решения пользователя | approval route |
| Legal deadlines/claims/POA | пользователь имеет legal visibility и ответственность | legal object |
| Notifications | реальное непрочитанное actionable событие, не дубль уже показанного | notification target |
| Finance obligations | `finance_section` либо разрешённый `finance_analytics`, пользователь связан/ответственен по существующей логике | `/finance` или `/summary?kind=money` |
| Finance questions | пользователь участник/ответственный по текущему модулю | `/finance/questions/:id` |
| Support | свой ответ/запрошены данные; support admin — назначенные/очередь | `/support/:id` или `/support/admin` |
| Security alerts | только security_audit и реально открытый alert | security route |

Нельзя делать пользователя ответственным за платёж только потому, что он менеджер сделки, если в финансовой модели нет такого правила. Для финансового совета использовать существующие сервисы и их visibility, а не новый признак «ответственный», придуманный по роли.

## 4. Использование существующего кода

### 4.1 Workplace

Предпочтительный путь — выделить из `backend/app/api/workplace.py` небольшие selectors/services без изменения существующего response contract, затем использовать уже отфильтрованный DTO. Не копировать весь монолитный файл в `briefing.py`.

Если быстрый безопасный срез строится из существующего `workplace` response:

- использовать только элементы с фактическим source ID, URL, due и type;
- не превращать визуальный KPI без действия в совет;
- не раскрывать данные через повторный запрос без прав;
- избегать рекурсии `briefing → workplace → briefing`: базовый builder не включает briefing block.

### 4.2 Финансы

Использовать `finance.obligations.query`, `finance.overview.build`, `finance.debt.build`, `finance.cashview` и `finance.access.Visibility` по необходимости. Для пользователя только с `finance_analytics` допустим cashview и `/summary?kind=money`; скрытые заводские/закупочные значения не попадают в текст.

Текст «Связаться с бухгалтерией» допустим как общий рекомендуемый шаг по реально наступающему платежу, но без выдуманного контакта. Если есть назначенный ответственный, показать его разрешённое имя; если нет — «ответственному за платёж».

## 5. DTO элемента

```json
{
  "item_key": "task:<SOURCE_ID>",
  "source_type": "task",
  "source_id": "<SOURCE_ID>",
  "source_signature": "<SHA256>",
  "severity": "critical",
  "title": "<ФАКТИЧЕСКОЕ_ДЕЙСТВИЕ>",
  "reason": "<ПОЧЕМУ_ВАЖНО>",
  "advice_text": "<СЛЕДУЮЩИЙ_ШАГ>",
  "due_date": "<YYYY-MM-DD|null>",
  "due_label": "Просрочено на 2 дня",
  "source_label": "Задача",
  "url": "<СУЩЕСТВУЮЩИЙ_ROUTE>",
  "amount": null,
  "currency": null,
  "pinned": false,
  "snoozed_until": null,
  "hidden": false
}
```

- Сумма — decimal string с валютой; не смешивать валюты.
- `url` генерируется сервером из известного route, не берётся из произвольного текста источника.
- `source_signature` рассчитывается из значимых полей: статус, срок, остаток, assignee. Изменение комментария без смысла не обязано возвращать скрытый элемент.
- Пользовательский DTO не содержит internal fields, hidden deal data и полный source payload.

## 6. Приоритизация

Для каждого candidate рассчитать детерминированный rank:

1. **critical:** просрочено и блокирует работу, либо открытый критичный security/support сигнал в зоне пользователя;
2. **high:** требуется сегодня либо ожидает решения пользователя;
3. **medium:** срок завтра;
4. **info:** ближайшие три дня и дополнительные критичные сигналы качества данных.

Внутри severity:

- действие, ожидающее именно пользователя, выше пассивного уведомления;
- более ранний срок выше;
- pinned выше непinned внутри того же severity;
- стабильный item_key для детерминированного порядка.

Pinned не может навсегда вытеснить новый более критичный элемент. Показать 3–5; при большем количестве — «Ещё N требуют внимания» со ссылкой на соответствующий рабочий список, без раскрытия скрытых counts.

Дедупликация: одна задача не появляется одновременно как task, notification и workplace focus. Выбирается наиболее содержательный source, остальные объединяются в reason. Платёж и задача связываются только по реальной существующей связи, не по совпадению слов.

## 7. Правила текста

Каждый элемент отвечает на три вопроса:

- **Что:** «Подготовить отчёт по таможне для самосвала».
- **Почему/когда:** «Срок — сегодня; задача просрочена на…» по фактическому due.
- **Следующий шаг:** «Открыть задачу, проверить вложения и отметить результат».

Запрещено:

- «завтра утром совещание», если события нет;
- «срочно свяжитесь с Ивановым», если такой ответственный не указан;
- «это заблокирует оплату», если связи нет;
- придумывать сумму, дату, договор, приоритет или вероятность;
- давать юридические/финансовые категоричные заключения без источника.

Допустимые шаблоны привязываются к `source_type`. Не использовать эмоциональное давление и оценку сотрудника. При отсутствии совета безопасный шаг — «Открыть источник и проверить детали».

## 8. Pin, snooze и hide

### Pin

`POST /api/briefing/items/{item_key}/pin` с `source_signature`. Хранится для текущей версии. Unpin аналогично. Item key валидируется против candidate текущего пользователя, чтобы нельзя было создавать произвольные ссылки/чужие состояния.

### Snooze

До конкретной даты, максимум например 30 дней. Критичный просроченный элемент можно отложить, но в UI остаётся ненавязчивый индикатор «N отложено». Наступление существенного изменения источника отменяет snooze: новый signature. Snooze не меняет срок задачи/платежа.

### Hide

Скрывает только текущую `source_signature`. Существенное изменение срока, статуса, остатка или assignee возвращает элемент. Скрытие не удаляет источник и не отмечает работу выполненной.

### Reset

«Показать скрытые и отложенные» открывает список состояний текущего пользователя с возможностью сброса. Не требуется сложный отдельный архив в первом срезе, но не должно быть необратимого hide.

## 9. Пустые, ошибочные и stale состояния

- Нет элементов: «Срочных дел по вашим задачам и срокам нет» + дата формирования.
- Один источник недоступен: показать остальные и warning «Часть данных не обновлена: <безопасное название>». Не выдумывать полную сводку.
- Критичный сервис финансов упал: не подменять его нулём; warning для пользователя с соответствующим правом.
- Вся сводка не рассчитана: ошибка блока не ломает остальной workplace.
- Данные устарели: фактический generated_at и retry.
- После выполнения источника элемент исчезает без необходимости вручную скрывать.

## 10. Необязательное ИИ-оформление

По умолчанию `BRIEFING_AI_REWRITE=false`.

Если владелец включил:

1. Сначала `briefing.build()` рассчитывает facts/rank/URL/amount/due.
2. Внешний/внутренний LLM получает только минимальный whitelist текст уже разрешённых 3–5 элементов.
3. Модель может изменить только `advice_text` и приветствие.
4. Validator сравнивает числа, даты, IDs, URLs и severity с оригиналом; при отличии используется детерминированный текст.
5. Нет новых элементов, источников или обещаний. Fallback мгновенный при timeout.

Приветствие «Добрый день» зависит от локального времени пользователя; не генерировать его как факт анализа. Имя пользователя берётся из разрешённого профиля.

## 11. API и права

- `GET /api/briefing` — текущий пользователь;
- `POST /api/briefing/items/{item_key}/pin`;
- `DELETE /api/briefing/items/{item_key}/pin`;
- `POST /api/briefing/items/{item_key}/snooze` — `until`, `source_signature`;
- `POST /api/briefing/items/{item_key}/hide`;
- `POST /api/briefing/items/reset` — выбранные/all своих состояний.

Специального `briefing_admin` не нужно. Право просмотра — любой активный пользователь, но состав строго персонален. `assistant_use` не требуется для детерминированной сводки; AI rewrite зависит от отдельной политики.

## 12. Производительность

- Не дублировать тяжёлые finance/workplace queries несколько раз на один page load.
- Выделить общий request-scoped context либо вычислять briefing внутри существующего workplace build.
- Измерить backend response p95 до/после на synthetic dataset; не допускать N+1 по кандидатам.
- Внешний AI rewrite не блокирует основной workplace: сначала детерминированный блок, дополнительное оформление по желанию и только при явной настройке.
- Actions короткие, indexed unique key; повторный click идемпотентен.

## 13. Приёмочные сценарии

1. Просроченная задача появляется выше задачи на завтра; после выполнения исчезает.
2. Просроченный платёж и сумма совпадают с существующим finance endpoint для той же роли и fixtures.
3. Менеджер без `cost/payment_terms/finance_section` не видит закрытые суммы/названия.
4. Пользователь с `finance_analytics` получает только разрешённый cashview и правильную ссылку.
5. Нет реального совещания — фраза о нём отсутствует.
6. Pinned не вытесняет новый critical.
7. Snooze/hide действуют только на текущего пользователя и текущую signature; изменение due возвращает элемент.
8. Acting_for показывает разрешённые дела с явным обозначением «по замещению» и не раскрывает остальные.
9. Support admin видит просроченную очередь; обычный сотрудник — только свой ticket.
10. Provider off не меняет состав, суммы, даты и ссылки.
11. Сохранённая старая workplace layout не сбрасывается.
12. 390/768/1280/1440 px: блок читаем, кнопки реально работают, нет горизонтального переполнения.
