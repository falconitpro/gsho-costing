# Эксплуатационные инструкции и runbook’и

## 1. Разделение ответственности

**Владелец:** облачные панели, секреты, production deploy/migrations, MFA required, external AI policy, подтверждение restore и отключение Timeweb.

**Claude/разработчик:** код, аддитивные migrations, tests, PR, sanitized отчёты и исправления. Не выполняет production/destructive действия без отдельного подтверждения.

**Security admin:** сессии, MFA reset, offboarding, access review, alerts. Не получает автоматически support/AI содержимое.

**Support specialist:** внутренняя очередь без почты.

## 2. Ежедневный контроль backup

Пользователь с `backup_status` открывает Настройки → Резервные копии:

- последний успех моложе 26 часов;
- причина daily/pre_deploy, snapshot ID и check;
- нет failed/stale;
- следующий запуск 19:00 Москва.

На сервере администратор использует безопасные команды:

```bash
systemctl status gsho-backup.timer --no-pager
systemctl list-timers gsho-backup.timer --no-pager
journalctl -u gsho-backup.service --since "26 hours ago" --no-pager
```

Не выполнять `journalctl … | grep -i password` с выводом в общий чат; если нужен отчёт, передать только sanitized error code/time. Не запускать `printenv`, не публиковать env.

Ручной запуск:

```bash
sudo systemctl start gsho-backup.service
sudo systemctl status gsho-backup.service --no-pager
```

`start` возвращается после завершения oneshot; проверить фактический status/restic snapshots, а не только отсутствие ошибки команды.

## 3. Проверка целостности

Периодически, в согласованное окно:

```bash
sudo systemctl start gsho-backup.service
# Отдельная защищённая команда администратора с EnvironmentFile:
# restic check
```

В коде предусмотреть отдельный systemd service для check, чтобы не передавать секреты в командной строке и не запускать интерактивный `source` с историей. Для глубокого `--read-data-subset` учитывать трафик/стоимость/время.

Ежемесячно проверять:

- свободное место staging;
- размер/рост bucket и расходы;
- свежесть signatures ClamAV;
- доступность RESTIC_PASSWORD в secret manager;
- отсутствие лишних IAM bindings;
- две последние успешные копии и отсутствие старых локальных постоянных архивов после перехода.

## 4. Полный runbook восстановления на recovery-ВМ

### 4.1 Предусловия

- авария либо плановый drill зафиксированы;
- выбран snapshot по дате, а не автоматически последний;
- чистая isolated recovery-ВМ, отдельный project/network;
- restore SA `storage.viewer` только на backup bucket;
- RESTIC_PASSWORD получен из secret manager;
- production backup writer на recovery отсутствует;
- production deploy timers/mail/WeCom/LLM/webhooks отключены;
- достаточно места и совместимые PostgreSQL 16/restic versions.

### 4.2 Восстановление артефактов

В защищённом recovery env, без вывода secrets:

1. Проверить `restic snapshots`.
2. Выбрать `<SNAPSHOT_ID>`, записать его в отчёт.
3. `restic check` по возможности до restore.
4. `restic restore <SNAPSHOT_ID> --target <RECOVERY_DIR>`.
5. Проверить manifest SHA-256 и `pg_restore --list <DUMP>`.
6. Если hash не совпал — остановиться, recovery данные не запускать.

### 4.3 PostgreSQL

1. Создать новый PostgreSQL 16 cluster/container с отдельным recovery password и без публичного порта.
2. Убедиться, что DSN/host указывает на recovery, а не production. Два независимых человека либо явный automated assertion проверяют это.
3. Создать пустую целевую DB и выполнить `pg_restore` custom dump с подходящими `--clean` только если это новая пустая recovery DB; на production такие параметры запрещены.
4. Применить change set’ы, которых нет по manifest schema revision, в зафиксированном порядке. Не применять миграции «на всякий случай» к production.
5. Собрать table counts/schema version. Не копировать данные в отчёт.

### 4.4 Файлы и приложение

1. Распаковать storage в новый recovery volume.
2. Сверить число файлов/размеры/SHA-256 manifest. Проверить sample hashes без открытия содержимого в чате.
3. Установить `APP_ENV=recovery`, `DATA_CLASSIFICATION=recovery`, отдельные JWT/MFA/storage credentials по recovery policy.
4. Отключить public ingress либо ограничить allowlist владельца.
5. Запустить backend/frontend; проверить health, schema, read-only smoke, selected attachments через authorised recovery test user.
6. Убедиться, что mail/WeCom/LLM/deploy/scheduled business jobs не выполнялись. Network egress deny предпочтителен.

### 4.5 Критерии успеха

- [ ] database restore завершился без ошибок;
- [ ] schema/table counts соответствуют ожиданию;
- [ ] файлы и hashes соответствуют;
- [ ] health/read smoke успешны;
- [ ] права/auth работают, production sessions не считаются автоматически безопасными для recovery;
- [ ] внешние побочные эффекты отсутствуют;
- [ ] время RTO и размер/RPO зафиксированы;
- [ ] sanitized отчёт приложен к журналу;
- [ ] recovery среда удалена/изолирована после приёмки.

Если восстановление выполняется для реальной аварийной смены production, дальнейший cutover — отдельный план владельца с DNS/IP, secrets, smoke и rollback. Этот документ не разрешает автоматический cutover.

## 5. Gate и отключение Timeweb

### 5.1 Проверка перед отключением

Повторить checklist из `03`: две daily, check, restore на итоговой схеме, владелец подтвердил. Записать дату/время и snapshot ID.

### 5.2 Удаление старого Compose service

1. PR удаляет только service `backup` и устаревшие инструкции постоянного локального хранения.
2. После merge владелец делает pre-deploy Yandex backup.
3. Обновить Compose services без `--volumes`, без `down -v`.
4. Проверить `pgdata`, `storage`, backend/frontend/db health и Yandex timer.
5. Не удалять Docker volume `backups` автоматически.

### 5.3 Provider backups Timeweb

Владелец вручную открывает панель Timeweb и отключает дополнительные/provider backups, если они есть. Код и Claude не имеют доступа к панели. Сохранить только факт/дату отключения, без screenshots личного кабинета с платёжными данными.

### 5.4 Старые локальные архивы

После согласованной страховочной паузы и ещё одного успешного Yandex run:

- инвентаризировать только старый backup volume;
- проверить, что путь не `pgdata` и не `storage`;
- удалить старые архивы точечной заранее показанной владельцу командой;
- сам volume можно оставить пустым для минимального риска;
- подтвердить, что текущий restic staging не находится в этом volume и не удалён.

Запрещено: `docker compose down -v`, `docker volume rm` по неясному имени, массовый `rm -rf` с переменной без проверки.

## 6. Сбой backup

### Последний run failed

1. Не отключать старые копии, если переход ещё идёт.
2. Проверить host status/journal sanitized: network/auth/disk/pg_dump/files/restic/check/prune.
3. При auth error — проверить IAM/ключ через панель, не пересылать secret.
4. При disk error — остановить повторяющиеся попытки, освободить только staging по runbook.
5. После исправления запустить manual, check, убедиться в новом success.
6. Закрыть alert с комментарием и root cause.

### Нет успеха >26 часов

Это high-priority эксплуатационный инцидент. In-app alert недоступен при полном падении сервера, поэтому владелец должен периодически проверять host timer; отдельный heartbeat рекомендуется как следующий improvement и не считается реализованным.

### Ошибка prune после успешной копии

Не удалять snapshot вручную. Отметить backup success + retention warning, проверить Object Lock/lifecycle/permissions, повторить forget/prune в controlled окне после исправления. Следить за ростом стоимости.

## 7. Ротация ключей и секретов

### Yandex backup key

1. Создать новый static key для того же узкого backup SA.
2. Обновить protected env на production через secret process.
3. Выполнить manual backup/check.
4. Удалить старый key только после успеха.
5. Проверить отсутствие старого key в git/logs/отчётах.

### Restore key

Хранить отдельно; rotation не должна требовать production writer. После смены выполнить read/list test на recovery.

### RESTIC_PASSWORD

Restic password не меняется простой заменой env для существующего репозитория. Для смены использовать документированный `restic key passwd` с новым дополнительным паролем/удалением старого key slot после проверки, либо новый repository по отдельному плану. Перед операцией обеспечить работающий старый секрет и restore test. Не выполнять по памяти на единственной копии.

### MFA encryption key

Поддержать `key_id` и rotation с расшифровкой старых/шифрованием новых после backup. Потеря ключа может заблокировать MFA; не хранить его только на той же ВМ.

## 8. Инцидент безопасности

### Подозрение на утечку/скомпрометированного сотрудника

1. Security admin выполняет revoke-all для пользователя; при необходимости offboard.
2. Сохранить SecurityEvent/Alert, request IDs, временной диапазон; не редактировать историю.
3. Проверить exports/downloads, role/MFA changes, active delegations/overrides.
4. Сбросить пароль/MFA по controlled flow, при компрометации admin — использовать break-glass процедуру владельца.
5. При подозрении на S3/JWT/RESTIC key — ротация по отдельному runbook и проверка bucket logs/backup integrity.
6. Не удалять production DB/logs и не восстанавливать поверх production до отдельного плана.
7. Зафиксировать решения и сроки в журнале; содержимое support/AI запрашивается только по законному отдельному доступу владельца, а не автоматически security role.

### Infected upload

Файл остаётся недоступным, quarantine обрабатывается scanner policy. Сохранить hash/engine/signature/time/uploader, уведомить security admin, проверить скачивания до обнаружения. Не отправлять infected sample в Claude/внешние чаты.

### Scanner outage

Новые uploads временно недоступны — это ожидаемый fail-closed. Восстановить clamd/signatures/resources, проверить pending retry. Не включать обходной `SCAN_BYPASS=true` на production.

## 9. Offboarding — операционный чеклист

1. Получить подтверждение увольнения/отключения от владельца.
2. Открыть сотрудника, проверить counts задач/approvals/finance questions/support tickets.
3. Назначить ответственного за последующее переназначение, но не выбирать автоматически исполнителя.
4. Выполнить «Отключить доступ» с step-up.
5. Проверить old session 401, завершение замещений/overrides.
6. Переназначить бизнес-задачи вручную ответственным ролям.
7. Обработать support queue и finance questions.
8. Включить сотрудника в ближайший access review как отключённого/проверенного.
9. При возврате — отдельная reactivation, не восстановление старых сессий.

## 10. Пересмотр прав — ежеквартально

- создать campaign, назначить reviewers и due;
- особое внимание security/support/finance/legal/AI/backup rights и временные overrides;
- проверить неактивных 30/60/90 дней по принятой политике;
- оформить keep/change/disable;
- собственные повышенные права — второй reviewer;
- после завершения сохранить progress/diff и просрочки;
- не удалять исторические AccessRule/Overrides без необходимости.

## 11. Поддержка — эксплуатация

Ежедневно специалист проверяет `/support/admin`: new, overdue, waiting reporter, unassigned. Ответы и решения остаются в ticket. Внешняя почта не используется.

Если сотрудник сообщил о баге вне CRM, специалист просит создать ticket либо создаёт от своего имени с явным описанием, но не получает доступ к чужой истории. Для системного инцидента связанные tickets можно закрывать отдельно с одинаковым решением, без массового удаления.

Метаданные/attachments хранятся по общей retention policy. Пользователей предупреждают не прикладывать secrets. Обнаруженный секрет не копировать в ответ; инициировать rotation и ограниченное удаление по отдельной процедуре.

## 12. ИИ — эксплуатация

- По умолчанию provider none. Включение external только после подтверждения владельца и проверки data policy.
- Еженедельно просматривать агрегаты: errors, quota, latency, fallback, tool denied, без чтения чужих диалогов.
- Проверять retention job и удаление.
- При изменении прав/finance formulas выполнить tool parity tests.
- При смене UI обновить help index.
- При инциденте provider отключить `ASSISTANT_PROVIDER=none`; сводка/help продолжат работу.
- Не копировать production prompts в Claude для отладки; создать synthetic reproduction по tool audit metadata.

## 13. Сводка — эксплуатация

Если пользователь сообщает о неверном совете:

1. Получить item_key/source_type/source ID и generated_at, не полный закрытый payload.
2. Сравнить с источником и правами пользователя.
3. Проверить due/rank/dedup/signature и deep link.
4. Исправить deterministic mapping/template, добавить fixture.
5. Не «лечить» неверные данные дополнительным LLM prompt.

## 14. Действия после потери Claude/GitHub

Этот пакет не создаёт отдельную систему разработки. Для эксплуатации важно:

- production код и migrations находятся в репозитории и на сервере;
- владелец хранит собственную защищённую копию git bundle/release архивов и документации вне диалога, без secrets;
- backup/restore не зависит от Claude;
- systemd, runbook и secret manager доступны администратору сервера;
- любой разработчик может работать по docs/operations с локальным clone и synthetic tests.

Не скачивать production dump для «архива разработчика» и не помещать secrets в git bundle.
