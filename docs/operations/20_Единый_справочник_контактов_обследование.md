# Единый справочник контактов: обследование (D-187)

Основание: решение владельца «Единый справочник контактов для КП и юридического профиля» v1.0 от 26.11.2026, раздел 11. Ответы владельца 26.11:
1. модель — на усмотрение разработчика;
2. удаление по запросу — обезличиванием;
3. начать с обследования.

Версия кода: 2f8ef30 (main = verified).

## 1. Где сейчас живут контакты клиента и кто их читает

| Источник | Где хранится | Кто пишет | Кто читает |
|---|---|---|---|
| **Прежний список карточки клиента** | `clients.contacts` (JSON: name, position, phone, email) | только создание клиента (`POST /api/refs/clients`, поле `contacts`); экрана правки нет | `GET /api/deals/{id}/kp/recipients` — список адресатов КП; `_finalize_approval` — автоматический черновик письма с КП **всем** контактам при утверждении; `ensure_profiles` — копирует их в юр. профиль при его создании; `contacts_import` (K-1) |
| **Контакты юридического профиля** | `legal_profiles.contacts` (JSON) у профилей client / factory / own | экран «Юридический профиль» (`LegalProfileBlock`, таблица «Контактные лица»), `PUT /api/legal/profiles/{id}` | `requisites_view` — телефон и почта **первого** контакта идут в «Реквизиты контракта» сделки; `party_from_profile` — то же в стороны договора (`legal_packages`); `legal_card` — таблица в «Карточке компании» (docx) |
| **Доверенности юр. профиля** | `legal_profiles.powers_of_attorney` (JSON: person, number, issued_on, valid_until, scope, attachment_id) | тот же экран | карточка компании, юр. пакеты |
| **Подписант** | `legal_profiles.signatory_name / _position / _basis`, `director` | тот же экран, ЕГРЮЛ | договоры, пакеты — **не контакт, остаётся в профиле** |
| **Новый справочник (K-1)** | `client_contacts` + журнал просмотров `client_contact_views` | экран «Контактные лица» карточки клиента, `contacts_import` | только сам справочник |

Контакты поставщиков (`factories.contacts`, роли rfq/sales/…) и сотрудников (`users.contacts`) — отдельные контуры. В объём пакета не входят.

## 2. Отправка КП сейчас
- `GET /kp/recipients` отдаёт контакты с почтой из прежнего списка.
- Два экрана выбора:
  - «Действия с КП» (`KpActions`): **заранее отмечен первый** адресат, есть свободное поле «ещё адреса»;
  - «Торги» (`NegotiationTab`): **все** адреса заранее подставлены в поле «Кому».
- `POST /kp/send`: письмо из системы, только если подключена почта. На рабочем сервере почта пока не подключена, поэтому КП выгружают и отмечают «отправлено вручную».
- **Ошибка:** «Копия» складывается в «Кому» — `to = body.to + body.cc`. Все адресаты получают письмо как основные.
- Сейчас «снимок» отправки — это запись в ленте сделки (адреса строкой) и запись в журнале действий (`to`, формат, номер письма). Имён, должностей, «Кому / Копия» и связи с контактом нет.
- **Расходится с решением владельца** (ничего не отправлять автоматически, ничего не отмечать заранее):
  - черновик письма при утверждении — всем контактам;
  - заранее отмеченный первый адресат или все адресаты;
  - свободный ввод адресов в обход справочника.

## 3. Объёмы на рабочем сервере
Скрипт `scripts/contacts_inventory.py` только читает базу и выводит одни количества, без персональных данных. Что он считает:
- прежний список и контакты юр. профилей: всего, без ФИО, почта с ошибкой, ни почты ни телефона, совпадения со справочником по почте / по телефону / **только по ФИО (вручную)**, новые;
- доверенности, подписанты;
- отправки КП в ленте.

Известно на 26.11: в прежнем списке был 1 клиент с 1 контактом, он перенесён в справочник. Остальное покажет запуск скрипта.

## 4. Модель: использовать / расширить / новое

| Сущность решения | Решение | Обоснование |
|---|---|---|
| Organization / Client | **использовать** `clients` и юр. профили | реквизиты не переносятся |
| Contact (человек) | **расширить** `client_contacts` | создан в K-1, в рабочей базе 1 запись; второй справочник не создаём |
| OrganizationContact / ContactRole | **новое**: `client_contact_links` (контакт, клиент, площадка, роли, основной, «с — по», активна, подтверждение) | один человек — несколько организаций с разными ролями и сроками (п. 2.2). Поля `client_id / roles / site_id / is_primary` переезжают из контакта в связь: сначала расширение и заполнение, затем переключение; старые столбцы — в отдельной задаче завершения |
| ContactMethod | **расширить**: `client_contacts.extra_emails` (список {адрес, пометка}) | в КП выбирается конкретный адрес. Отдельная таблица каналов — когда понадобятся периоды и подтверждение по каналу |
| LegalAuthority | **расширить** доверенности юр. профиля: в запись добавляется `contact_id`, статус «действует / истекла» считается по `valid_until` | список доверенностей уже есть, с документом и сроком |
| Телефон и почта организации для договоров | **новое**: `legal_profiles.org_phone / org_email` | сейчас в договор попадают телефон и почта первого «контактного лица». Это данные организации, а не человека. При переносе заполняются из первого контакта, чтобы договоры не изменились; юрист проверяет |
| Снимок отправки КП | **новое**: `kp_dispatches` (сделка, версия, способ: система / вручную, кто, когда, номер письма, ключ повтора) и `kp_dispatch_recipients` (Кому / Копия, порядок, contact_id, link_id, имя, должность, адрес на момент отправки) | неизменяемая история; повтор с тем же ключом новую запись не создаёт |
| История изменений контакта | **новое**: `client_contact_history` (поле, было, стало, кто, когда) | доступ — по группе «Клиенты: контактные лица»; при обезличивании стирается. В общем журнале действий персональных данных по-прежнему нет |
| Удаление по запросу | **изменить**: обезличивание вместо удаления (`anonymized_at`). Запись с тем же id остаётся, ФИО, телефон, почта и история стираются, связи закрываются | решение владельца 2: ссылки и снимки отправленных КП не рвутся |

## 5. Перенос (одноразовый, по разделу 5 решения)
- Источники: прежний список карточки клиента и контакты юр. профилей клиентов.
- Профили собственных компаний и поставщиков не переносятся.
- Ключ источника: клиент или профиль плюс порядковый номер и отпечаток записи. Таблица соответствия «источник → контакт → связь» сохраняется.
- Сопоставление: точная почта у того же клиента → нормализованный телефон у того же клиента → **только ФИО = неоднозначно, в ручной разбор**.
  - Исправить и `contacts_import` (K-1): сейчас он объединяет по ФИО, если нет почты и телефона.
- Порядок: пробный прогон с отчётом → перенос на стенде (test.dobrov.pro) → приёмка → копия → разовый перенос на рабочем сервере.
- Переключение возможно только при нуле неразобранных неоднозначных совпадений.
- После переключения прежний список и таблица контактов юр. профиля — только для чтения. Удаление — отдельной задачей.

## 6. Что меняется в КП и юр. профиле
- **КП:** адресаты — из справочника, с фильтром по ролям; заранее ничего не отмечено. «Кому» и «Копия» раздельно, у контакта с несколькими адресами выбирается конкретный. Предпросмотр перед отправкой. Снимок сохраняется и при отправке из системы, и при отметке «отправлено вручную». Автоматический черновик при утверждении убирается. Свободные адреса — только через «Добавить контакт».
- **Юр. профиль:** вместо таблицы «Контактные лица» — контакты клиента с юридическими ролями, переход в карточку контакта.
  - Новые роли контакта: руководитель, представитель по доверенности, юридически значимая переписка, договоры и документы, юридический отдел.
  - Предупреждение, если доверенность истекла.
  - Подписант, основание и реквизиты — без изменений.

## 8. Откат и остановка
- Миграции только расширяют схему, прежние поля не меняются до задачи завершения. Откат — возврат приложения на предыдущую версию через `update.sh`, данные новых таблиц остаются.
- Перед переносом на рабочем сервере — обычная копия `update.sh` плюс отдельная проверочная копия.
- **Остановить переключение, если:**
  - есть неразобранные неоднозначные совпадения;
  - не совпадают количества;
  - не проходит сквозной сценарий КП на стенде;
  - проверка схемы показывает расхождения.

## 9. Этапы
