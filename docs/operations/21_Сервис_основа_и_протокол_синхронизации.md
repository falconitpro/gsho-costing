# Сервисная служба — основа (I-0) и протокол синхронизации

Версия 1.0 · 27.11.2026 · D-191. Экранов в I-0 нет: они появятся в I-1, только в новом виде. Здесь — модель данных, права, правила и протокол, общие для веба и будущего приложения инженера без сети (I-4).

## 1. Модель данных (migrations/060)

| Таблица | Что хранит | Связи |
|---|---|---|
| `service_requests` | Обращение клиента: номер СО-ГГГГ-NNNN, канал, вид, категория срока реакции, «машина стоит», описание, статус | клиент, площадка, машина, контакт |
| `work_orders` | Заказ-наряд НР-ГГГГ-NNNN: статус, инженер, кто назначил, плановые сроки, **version**, подпись клиента, дата закрытия | обращение, клиент, площадка, машина, вид работ |
| `work_order_events` | Каждое действие с нарядом. **Только добавление** — триггер в базе запрещает изменение и удаление | наряд, автор |
| `work_order_checklist_items` | Пункты чек-листа: из шаблона вида работ, отметка, кто и когда | наряд |
| `service_work_types` | Виды работ: категория, тип техники, норматив (ч), бригада, нужные допуски, шаблон чек-листа | — |
| `service_permits` | Допуски исполнителей со сроком действия | — |
| `service_sla_levels` | Сроки реакции: реакция, выезд, восстановление (ч), календарь 24×7 или рабочие часы | — |

Решения, учтённые в модели:
- **Машина** — существующая `client_machines`, второй таблицы машин нет. **Площадка** — `client_sites`, **контакт** — `client_contacts`. Связи проверяются: площадка и машина должны принадлежать клиенту обращения.
- **Пустое — не 0.** Норматив и сроки, которые не заданы, хранятся пустыми.
- **Обращение** становится «принято», когда по нему создан наряд, и «выполнено», когда наряд закрыт. Отменённый наряд обращение не закрывает.

## 2. Статусы наряда

| Действие | Из статуса | В статус | Кто |
|---|---|---|---|
| Назначить инженера | черновик (или переназначить — из любого незакрытого) | назначен | руководитель |
| Начать | назначен | в работе | инженер, руководитель |
| Приостановить / возобновить | в работе / приостановлен | приостановлен / в работе | инженер, руководитель |
| Готов к закрытию | в работе | готов к закрытию | инженер, руководитель |
| Вернуть в работу | готов к закрытию | в работе | инженер, руководитель |
| Закрыть | в работе, готов к закрытию | закрыт | инженер, руководитель |
| Отменить (с причиной) | черновик, назначен, в работе, приостановлен | отменён | руководитель |

- **«Готов к закрытию»** и **«Закрыть»** требуют, чтобы все обязательные пункты чек-листа были отмечены.
- **Закрытие:** нужна подпись представителя клиента (ФИО). Без связи закрытие не проводится: наряд переходит в «готов к закрытию», подпись сохраняется. Окончательно его закрывают на связи (решение 5).
- **Закрытый и отменённый наряд** не меняется. Принимаются только заметки с поля, чтобы они не потерялись.

## 3. Права

| Действие | Кто |
|---|---|
| Справочники: читать | группа «Сервис: справочники», чтение (инженер — да) |
| Справочники: править и утверждать черновик | та же группа, правка (руководитель сервиса, ЗГД); инженер — нет |
| Обращения: видеть | группа «Сервис: обращения и наряды», чтение; инженер — нет |
| Обращения: заводить | та же группа, правка |
| Обращения: отклонять, создавать наряды, назначать инженера, сроки, отмена, решение конфликтов | руководитель сервиса и ЗГД (правка группы, роль не «только инженер») |
| Начать, приостановить, готов, вернуть, закрыть, чек-лист, заметки | назначенный инженер или руководитель |
| Видеть наряд | группа «чтение»; инженер — **только назначенные ему** (чужой наряд для него «не найден») |

Назначить можно только действующего сотрудника с ролью «Инженер» или «Руководитель сервиса». Новых ролей и изменений прав других разделов нет: используется матрица D-181.

## 4. Событие

```json
{ "id": "uuid, задаёт устройство", "kind": "start", "base_version": 7,
  "payload": {}, "device_id": "web | id устройства", "offline": false, "occurred_at": "время на устройстве" }
```

- **kind:**
  - `assign {engineer_id}`, `plan {planned_start, planned_end}`;
  - `start`, `hold`, `resume`, `ready`, `reopen`, `close {signed_by_name}`, `cancel {reason}`;
  - `note {text}`, `checklist {item_id, done, note}`;
  - `resolve {event_id, decision: accept | dismiss}`.
- **base_version** — версия наряда, которую видел отправитель.
- **id задаёт отправитель.** Повтор с тем же id ничего не меняет и возвращает прежний результат. Поэтому очередь можно безопасно отправлять повторно после обрыва связи. Тот же id у другого наряда, автора или вида действия — ошибка 422.
- **occurred_at** — только для истории. Порядок применения задаёт сервер: события применяются по одному, в порядке получения.
- **Результат:**
  - `applied` — применено;
  - `merged` — применено поверх изменений, которых отправитель не видел;
  - `conflict` — не применено, ждёт решения руководителя;
  - `rejected` — недопустимо, причина в `reason`.

  У применённого события есть `new_version`.

## 5. Конфликты — без «последняя запись побеждает»

| Отправитель видел старую версию, а после неё было… | Что происходит |
|---|---|
| Заметка — что угодно | объединяется |
| Отметка пункта чек-листа — этот же пункт отмечен иначе | **конфликт**; иначе объединяется |
| Смена статуса — была другая смена статуса, назначение или принятый конфликт | **конфликт**; иначе применяется, если переход допустим из текущего статуса |
| Назначение или сроки — было назначение или перенос сроков | **конфликт**; иначе объединяется |
| base_version больше серверной | отклонено |

- **Конфликт наряд не меняет.** Событие хранится с причиной, в реестре изменений появляется отметка `conflict`, у наряда растёт счётчик `conflicts`.
- **Решает руководитель** событием `resolve`:
  - `accept` — исходное действие выполняется над текущим нарядом с теми же проверками статусов и чек-листа;
  - `dismiss` — отклоняется.

  Решённый конфликт повторно не решается.
- **Запрещено без связи** (ТЗ): закрытие наряда — переводится в «готов к закрытию». Складские операции, утверждение сметы и изменение прав в сервисе появятся в I-3 и I-5 и будут отклоняться при `offline: true` по тому же правилу.

## 6. Синхронизация

| Запрос | Назначение |
|---|---|
| `POST /api/service/sync/push {events: [{order_id, …событие}]}` (до 500) | Отправить очередь. Каждое событие — в своей точке сохранения: ошибка одного (нет доступа, чужой наряд) не мешает остальным. Ответ — по событию: результат, причина, версия и статус наряда |
| `GET /api/service/sync/pull?cursor=N` | Наряды, изменившиеся после курсора, целиком: чек-лист, события, открытые конфликты — только видимые пользователю. Курсор — номер в реестре `change_events` |
| `GET /api/service/orders` | Полный список своих нарядов. Устройство сверяет его раз в сутки и при входе; наряд, переназначенный другому, из списка уходит |
| `POST /api/service/orders/{id}/events` | То же событие из веба, по одному |

Курсор надёжен: реестр отдаёт только события завершённых транзакций (горизонт xid, D-181). Поэтому медленная транзакция не «проскочит» мимо курсора.

## 7. Черновик справочников (решение 8)

- **Состав черновика:**
  - 10 допусков: электробезопасность III/IV, горные работы, подземные выработки, высота, ГПМ, огневые, давление, охрана труда, первая помощь;
  - 5 категорий срока реакции: критично, высокий, обычный, плановые, консультация;
  - 12 видов работ: диагностика, ТО-250/500/1000, ремонт двигателя, гидравлики, электрики, сварка, пусконаладка, ТО ПДМ в подземной выработке, консультация.
- **Нормативы и сроки — ориентир для обсуждения.** Каждая запись помечена «черновик», её утверждает руководитель сервиса (`PUT …/refs/{вид}/{id}` с `is_draft: false`). Утверждение записывается в журнал.
- **Загрузка:**
  - dev и стенд — автоматически;
  - рабочий сервер — `python -m scripts.service_refs_import`: пробный прогон, затем `--yes`, только по согласованию. Уже заведённые коды не меняются.
