# Функциональное ТЗ

## 1. Цель

Добавить в существующую БЕРГ-ХАУС CRM надёжное внешнее резервное копирование, управляемую безопасность сотрудников, внутреннюю поддержку, защищённого ИИ-помощника и персональную ежедневную сводку. Все функции используют текущие данные, права и интерфейс CRM; обучение сотрудников не должно требовать отдельной системы.

## 2. Термины и границы

- **Постоянная копия** — зашифрованный restic snapshot в Yandex Object Storage. Временный staging, status JSON и технические логи копией не являются.
- **Recovery-контур** — отдельная изолированная среда для проверки восстановления; не используется сотрудниками как dev/test.
- **Активная сессия** — запись `AuthSession`, не отозванная и не истёкшая по idle/absolute сроку; сам JWT в браузере без действующей записи недействителен.
- **Обращение** — внутренний ticket со сообщениями и вложениями, а не письмо и не фиктивная задача по сделке.
- **Tool** — серверная read-only функция с жёсткой схемой и авторизацией, вызываемая оркестратором ИИ.
- **Элемент сводки** — рекомендация, рассчитанная из фактически существующего источника. Не является самостоятельной задачей и не создаёт новых событий.
- **Реальные данные** — production-дампы, документы, персональные и коммерческие сведения, секреты, содержимое реальных диалогов и выгрузки.

Вне объёма: почта поддержки, изменение оплаты Timeweb, переезд CRM, независимый от GitHub процесс разработки, write-действия ИИ, автоматическое назначение нового исполнителя при увольнении, публичное файловое хранилище.

## 3. Пункт 2 — резервное копирование в Яндекс

### 3.1 Пользовательский результат

CRM ежедневно в 19:00 по Москве, включая субботу и воскресенье, создаёт зашифрованную копию PostgreSQL и файлов в Yandex Object Storage. Перед обновлением создаётся дополнительная копия. Временные файлы на сервере удаляются. Владелец видит дату последней успешной копии и ошибку, а при аварии может восстановить систему на отдельной ВМ.

### 3.2 Состав копии

- PostgreSQL: `pg_dump --format=custom`, не plain SQL;
- файлы текущего `STORAGE_PROVIDER=local`: архив содержимого volume `storage`;
- `manifest.json`: run ID, причина `daily|pre_deploy|manual`, начало/окончание UTC и Москва, git commit, версия схемы/последний change set, storage provider, размеры и SHA-256 артефактов, версия restic;
- при смене storage provider — отдельный адаптер; нельзя отметить копию успешной, если вложения фактически не включены;
- секреты `.env`, ключи RESTIC и пароли в копию в открытом виде не включаются. Для полного аварийного восстановления секреты хранятся отдельно в secret manager владельца.

### 3.3 Расписание и retention

- systemd timer: 19:00 `Europe/Moscow`, `Persistent=true`; пропущенный запуск выполняется после загрузки;
- параллельные запуски исключены lock’ом;
- pre-deploy backup обязателен после включения проверенного контура; ошибка копии останавливает обновление;
- `restic forget --keep-daily 90 --keep-monthly 12 --prune` после успешного backup, не вместо него;
- lifecycle не должен произвольно удалять текущие объекты restic. Допустимы согласованные правила для incomplete multipart и неактуальных версий;
- Object Lock по умолчанию не включать в первом срезе. Включение — отдельное решение после теста retention.

### 3.4 Наблюдаемость

- атомарный status JSON на хосте и best-effort запись `BackupRun` без секретов;
- экран «Настройки → Администрирование → Резервные копии»: последняя попытка, последний успех, snapshot ID, причина, размер, состояние check, время следующего запуска, ошибка без команд и credentials;
- in-app предупреждение при failed run и при отсутствии успеха более 26 часов;
- systemd journal сохраняет техническую ошибку; UI не выполняет shell и не показывает secret-bearing env;
- ручные действия владельца: «Проверить статус» и «Создать копию» только через контролируемый server-side механизм, без передачи произвольной команды. Если безопасный trigger не реализован, UI даёт точную инструкцию для SSH, а не мёртвую кнопку.

### 3.5 Восстановление и миграция с Timeweb

1. Настроить Яндекс и выполнить manual run, не меняя старый `backup`.
2. Получить минимум две успешные последовательные ежедневные копии.
3. Выполнить `restic check` и контроль SHA-256 manifest.
4. На чистой recovery-ВМ восстановить БД и файлы, применить change set’ы, открыть синтетическую проверочную учётную запись либо использовать специально подготовленный recovery smoke test. Все внешние интеграции отключены.
5. Сравнить контрольные количества таблиц, схему, хэши файлов, health endpoint и ключевые read-only API.
6. Получить явное подтверждение владельца.
7. Удалить старый сервис `backup` из Compose, не выполнять `down -v`; отключить provider backups вручную в панели Timeweb. Старый volume не удалять автоматически.
8. Включить обязательный pre-deploy backup и зафиксировать дату перехода.

## 4. Пункт 4 — безопасность и права

### 4.1 MFA

- TOTP по RFC-совместимому authenticator; секрет показывается только при настройке, хранится зашифрованным отдельным ключом.
- После правильного пароля выдаётся только короткий `mfa_pending` challenge на 5 минут, а не полноценная CRM-сессия.
- Поддержать QR/otpauth и ручной ввод секрета, часы сервера NTP, небольшой допустимый clock skew, rate limit и общую ошибку проверки.
- 10 одноразовых recovery codes, показ один раз, в БД только хэши; использованный код недействителен.
- Rollout: `optional` для проверки → `required` для всех парольных пользователей после подтверждения владельца. При required пользователь без MFA может только настроить MFA или выйти.
- OIDC не считается автоматически MFA. Проверить `amr/acr` и корпоративную политику; если подтверждения нет, требуется локальный TOTP.
- Сброс MFA другим сотрудником требует `security_admin=EDIT`, recent step-up, журнала, уведомления пользователю в системе и отзыва всех сессий. Нельзя оставить систему без последнего активного security admin.

### 4.2 Пароли

- минимум 12 символов, максимум 128; буквы и цифры обязательны, проверка локального denylist и совпадения с логином/именем;
- нельзя повторить последние 5 паролей; история хранится как хэши;
- admin-set пароль временный: `password_must_change=true`, одноразовая передача вне журнала, обязательная смена после входа;
- существующие PBKDF2-хэши проверяются прозрачно; новые параметры стойкости внедряются после benchmark и rehash при успешном входе, без массовой блокировки;
- обязательная периодическая смена без признаков компрометации не вводится;
- смена/сброс пароля отзывает остальные сессии; при собственной смене текущая сессия может быть перевыпущена после успешной проверки.

### 4.3 Сессии

Пользователь в «Настройки → Безопасность» видит текущую и другие сессии: создание, последняя активность, срок, IP/сеть по принятой политике приватности, сокращённый user-agent, MFA-статус. Он может завершить выбранную другую сессию и «все, кроме текущей». Logout отзывает текущую запись на сервере.

Security admin видит метаданные сессий сотрудников и может завершить одну или все сессии пользователя. Токен, cookie и секреты нигде не отображаются. Проверка записи `AuthSession` выполняется при каждом запросе; `last_seen_at` обновляется не чаще одного раза в 60 секунд.

### 4.4 Увольнение

Операция «Отключить доступ» выполняется атомарно:

- `users.is_active=false`;
- отозваны все сессии и MFA challenges;
- прекращены замещения, где сотрудник является замещаемым или заместителем;
- индивидуальные overrides закрыты по `valid_to`, история сохранена;
- открытые задачи помечены `needs_reassignment=true` без автоматического выбора нового исполнителя;
- назначенные support tickets и открытые finance questions попадают в очередь переназначения;
- создаются audit/security events с количеством затронутых объектов, но без закрытых payload;
- сохраняются пользователь, история, документы и авторство.

Повторное включение — отдельная операция с пересмотром ролей, новым входом и MFA. Нельзя отключить себя или последнего активного security admin.

### 4.5 Пересмотр прав

Ежеквартально security admin создаёт кампанию. Для каждого активного пользователя видны роли, overrides и их сроки, замещения, observer scope, MFA и активность. Решения: `keep`, `change`, `disable`; обязательны reviewer, дата и комментарий при change/disable. Собственные повышенные права подтверждает другой уполномоченный reviewer. Напоминания в CRM за 14/7/1 дней, просроченная кампания отмечается отдельно. Фактические изменения выполняются существующими access endpoints с security events, а не текстовой отметкой «проверено».

### 4.6 Скачивания, экспорт и алерты

Журналируются успешные и отклонённые попытки: actor, время, request/correlation ID, действие, entity ID, deal ID, формат, число строк, размер, результат, фильтры в sanitized form. Содержимое файлов, полные ответы, секреты, подписанные URL и закрытые значения не журналируются.

Начальные настраиваемые пороги предупреждения:

- 5 экспортов за 10 минут;
- выгрузка 1000 и более строк;
- 20 скачиваний закрытых документов за 10 минут;
- любое изменение ролей, overrides, MFA reset и offboarding — высокий приоритет без порога.

Это алерты, а не автоматическое обвинение или блокировка. Получатели — пользователи с `security_audit`; содержимое support/AI по этому праву не раскрывается. Дедупликация не должна скрывать продолжающуюся аномалию: событие обновляет count/last_seen.

### 4.7 Проверка файлов и ссылки

- Все новые пользовательские uploads проходят централизованный `secure_upload`: авторизация → лимит → quarantine → SHA-256 → ClamAV → clean → promote → доступ по ID.
- `pending` и `error` не выдаются; `infected` отклоняется, содержимое удаляется из quarantine, остаются только метаданные и хэш. Старые файлы получают `legacy_unscanned`, массово не блокируются.
- SVG/HTML и прочие активные форматы сохраняют текущую защиту `file_response`; антивирус её не заменяет.
- Сканер fail-closed для новых файлов, с timeout и ограничениями архивов. На ВМ 4 ГБ RAM сначала измеряются ресурсы; при нехватке памяти scanner выносится на отдельный worker, а не отключается.
- Закрытые документы выдаются только после серверной проверки. Постоянные публичные ссылки запрещены. Для S3 presigned URL — до 5 минут, не сохраняется как постоянный `storage_url`, выдаётся по attachment ID после проверки. Предпочтителен единый download endpoint.
- Сгенерированные CRM файлы не считаются пользовательским upload, но их скачивание журналируется.

### 4.8 Тестовые среды и ИИ

Production-дампы запрещены в обычном dev/test. Тестовые фикстуры синтетические; seed только явный и никогда автоматически на production. Recovery — исключение только на изолированной ВМ с отдельными credentials и отключёнными mail/WeCom/LLM/deploy. Внешнему ИИ отправляются минимальные разрешённые поля после фильтрации; режим по умолчанию для CRM-контекста — запрет, пока владелец отдельно не разрешил provider/data policy.

## 5. Пункт 5 — техподдержка внутри CRM

### 5.1 Создание обращения

Кнопка «Поддержка» доступна активному сотруднику в шапке и на рабочем месте. Форма: категория `error|question|access|improvement`, запрошенная срочность `normal|high|critical`, тема до 200 символов, описание до 8000, текущая страница, app commit, correlation ID, sanitized browser metadata, до 5 файлов по 50 МБ каждый. Автоматический route можно изменить до сохранения; текст ошибки и stack trace пользователь вставляет сам по решению.

После сохранения создаётся номер `SUP-YYYY-NNNN`, статус `new`, автор получает карточку и app-уведомление. Специалисты с `support_admin` получают app-уведомление. Почта не вызывается даже при наличии mail-каналов в карточке пользователя.

### 5.2 Работа автора

- список только своих обращений с фильтрами статуса и поиском по номеру/теме;
- карточка с историей сообщений, файлами, статусом, назначенным специалистом и timestamps;
- ответ на `waiting_reporter` переводит ticket в `in_progress`;
- после `resolved` автор может закрыть либо нажать «Проблема осталась» — возврат в `in_progress`;
- `closed` immutable; новая проблема — новое обращение с необязательной ссылкой на прежний номер;
- нельзя редактировать или удалять прошлые сообщения.

### 5.3 Работа специалиста

Очередь `/support/admin`: новые, в работе, ждут автора, решённые, просроченный первый ответ. Доступны назначение, внутренний приоритет, ответ, статусы `new|in_progress|waiting_reporter|resolved|closed`, фильтры и поиск. Назначенный уволенный специалист автоматически снимается, ticket возвращается в общую очередь с system message.

Первый ответ фиксируется один раз. Решение требует заполненного комментария/сообщения. Все изменения статуса и назначения создают system message, audit и app-only уведомления. Отдельное право `support_admin=READ` позволяет смотреть очередь, `EDIT` — обрабатывать. Роль admin без этого права получает 404 на чужую карточку.

### 5.4 SLA без почты

Начальные ориентиры, настраиваемые в CRM: первый ответ critical — 4 рабочих часа, high — 1 рабочий день, normal — 2 рабочих дня. Это внутренние ориентиры очереди, не обещание клиенту. Просрочка показывается badge и в сводке специалиста. Email escalation отсутствует.

## 6. Пункт 6 — ИИ-окно

### 6.1 Режимы

- **CRM:** вопросы по сделкам, оборудованию, задачам и финансам в пределах прав;
- **Справка:** как выполнить действие в системе, поиск по утверждённым локальным help-документам;
- **Общий вопрос:** без CRM-контекста и без скрытой передачи текущей страницы.

Пользователь видит активный режим. При `provider=none` CRM-данные можно получить детерминированными tools и help-search, а генеративный текст заменяется честным статусом. ИИ не имитирует ответ.

### 6.2 Примеры

- «Сколько стоило оборудование X в последних видимых мне предложениях?» — только история с соответствующим правом, дата, валюта, поставщик, источник и ссылка;
- «Сколько мы сейчас должны заказчику?» — уточнение направления/контрагента при необходимости; ответ из `finance.debt/obligations`, по валютам, остаток, дата расчёта, подтверждённое и временное разнесение отдельно;
- «Что мне сделать по сделке D-…?» — видимые задачи/этапы и ссылки, без автоматического изменения;
- «Как запросить уточнение в Финансах?» — help result с ссылкой на актуальный раздел;
- «Составь план переговоров» — general mode, без CRM-данных, если пользователь сам не ввёл разрешённый текст.

### 6.3 Ответ и ограничения

Структура: текст, режим, фактическая дата/валюта, источники с deep link, предупреждения, provider/fallback. Модель не добавляет источники сама. Данные tools ограничены 10 записями по умолчанию; для больших выборок предлагается открыть экран с фильтром, а не выгружать всю БД.

Запрещены произвольный SQL, чтение `.env`, filesystem/shell tools, межпользовательский просмотр диалогов, неявный support admin доступ, chain-of-thought logging и любые write actions. Rate limit, дневная квота, ограничение prompt/context и 30-дневный срок хранения диалогов по умолчанию. Пользователь может удалить свой диалог. Security audit видит технические метаданные, но не содержимое.

## 7. Пункт 7 — ежедневная сводка-подсказка

### 7.1 Состав

На рабочем месте появляется блок «Ваши приоритеты» с 3–5 элементами:

- что произошло и что требуется;
- фактический срок;
- почему это важно;
- конкретный рекомендуемый следующий шаг;
- источник и deep link;
- `critical|warning|info`, дата и время формирования.

Источники: текущие задачи и просрочки, acting_for, этапы, согласования, юридические сроки, claims, POA, уведомления, finance obligations/questions, support queue — только если пользователь имеет соответствующий доступ. Платёж поставщику появляется из финансового сервиса, а не из догадки по тексту задачи.

### 7.2 Приоритет

1. Просрочено и блокирует работу.
2. Требуется сегодня.
3. Ожидает решения пользователя.
4. Срок завтра.
5. Срок в ближайшие три дня.
6. Критичные признаки качества данных и security alerts, если они входят в зону пользователя.

Pinned учитывается внутри одного уровня критичности; более критичный новый элемент не исчезает под закреплёнными. При равенстве — раньше срок, затем стабильный item key.

### 7.3 Действия и обновление

- «Открыть» ведёт на источник;
- pin/unpin;
- snooze до выбранной даты;
- hide для текущей версии источника; существенное изменение срока/статуса создаёт новую сигнатуру и возвращает элемент;
- исчезновение/закрытие источника автоматически убирает элемент;
- GET строит свежую сводку при открытии рабочего места; после завершения задачи и других mutations frontend перезагружает данные;
- пустое состояние: «Срочных дел по вашим задачам и срокам нет». Не создавать искусственные советы.

Пример про совещание допустим только при реальном событии/задаче со сроком и связью. Если связи нет, фраза «завтра совещание» запрещена. Необязательный ИИ может переписать только `advice_text` уже рассчитанного элемента; суммы, даты, приоритет, источник и URL остаются детерминированными. При недоступном ИИ показывается обычный текст.

## 8. Общие нефункциональные требования

- API не раскрывает существование закрытого объекта: 404 там, где это принято в текущей CRM; отсутствие действия над разрешённым объектом — 403.
- Все mutations имеют авторизацию, валидацию, audit; критические операции — recent MFA step-up и защиту от повторного применения.
- Денежные значения в DTO остаются decimal strings, валюта обязательна; новые суммы не хранить как float.
- Даты в БД UTC; пользовательские сроки — локальная дата; расписания Москвы задавать timezone явно.
- Новые таблицы индексируются по пользователю, статусу, сроку и внешнему ключу согласно запросам. Не добавлять N+1 в массовые списки.
- Страницы работают на 1440/1280/768/390 px, keyboard accessible, с loading/empty/error/success состояниями.
- Внешний сбой ClamAV, LLM, S3 не приводит к молчаливому ослаблению защиты. Для backup и new files принцип fail-closed; для сводки — детерминированный fallback.
