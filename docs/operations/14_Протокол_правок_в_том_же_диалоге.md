# Протокол правок в том же диалоге с Claude

## 1. Основной принцип

После первого запуска пакета продолжай работу **в том же диалоге Claude**, где есть контекст кода, PR и отчётов. Не выгружай production-данные и секреты ради «обновления контекста». Все решения и фактические результаты фиксируются в репозитории `docs/operations/`, поэтому их можно восстановить даже при прерывании диалога.

## 2. Первое сообщение для начала

Скопируй в диалог с Claude содержимое `00_НАЧНИ_ЗДЕСЬ.md` и передай весь ZIP либо документы. Добавь:

```text
Работаем в существующем репозитории falconitpro/gsho-costing.
Сначала выполни этап 0, ничего не меняя на production. Прочитай весь пакет,
сверь актуальный main с baseline, затем покажи краткий план этапа 1 и начни
вертикальную реализацию. PR создавай в main, не сливай. Все проверки запускай
фактически и записывай результаты в журналы. Секреты и production-данные
в диалог не запрашивай и не выводи.
```

Если Claude имеет доступ к GitHub только через MCP, явно указать владельца/репозиторий и не предполагать, что локальный clone уже существует. Перед write operations подтвердить путь репозитория; не отправлять большие приватные файлы в ответ пользователю без необходимости.

## 3. Цикл каждого этапа

### 3.1 Перед кодом

Пользователь:

```text
Продолжаем в этом же диалоге. Начни этап <N>. Сначала сверь актуальный main,
обнови 16_Состояние_внедрения.md и назови предполагаемые файлы/миграции/риски.
Production и облачные панели не трогай.
```

Claude обязан:

- получить актуальный main и PR status;
- прочитать живые `15`–`17`;
- отметить этап `IN_PROGRESS`;
- перечислить фактические изменения и gate;
- проверить migration collision.

### 3.2 Во время работы

Не требовать промежуточные огромные dumps кода. Запрашивать короткие статусы:

```text
Дай статус по этапу: что уже изменено, какие проверки фактически запущены,
какие ошибки есть, что осталось. Не заявляй готовность по написанному коду.
```

При ошибке пользователь даёт только симптом и sanitized лог:

```text
Проверка <ID> падает. Воспроизведи на synthetic данных, найди первопричину,
исправь в той же ветке и повтори весь затронутый набор проверок. Обнови журнал.
```

Не обходить failing test удалением/ослаблением assertions. Если тест неверен, доказать это baseline/contract и отдельно описать исправление.

### 3.3 Перед PR

```text
Заверши этап только после полного checklist. Приложи PR в main, список коммитов,
фактические команды и численные результаты тестов/build/browser QA. Отдельно
перечисль мои действия и production-only gates. Обнови 15, 16 и отчёт по 17.
```

Пользователь проверяет и сливает PR сам. После merge:

```text
PR #<N> слит. Получи актуальный main, отметь merge commit и продолжи только
после сверки оставшихся замечаний. Не считай production rollout выполненным.
```

## 4. Действия владельца в Yandex/Timeweb

Секреты не передавать. Использовать статусы:

```text
Бакет и два SA созданы, роли назначены только на бакет. Ключи сохранил.
Выполни по репозиторию проверку инструкций и дай следующую безопасную команду
без запроса секретов. После ручного запуска передам sanitized status.
```

После запуска владелец передаёт только:

- время начала/окончания;
- success/failed;
- snapshot short ID;
- sanitized error code;
- результат `restic check`;
- размеры/hashes при необходимости.

После restore drill:

```text
Две последовательные ежедневные копии успешны. Check успешен. Восстановление
на отдельной recovery-ВМ выполнено, БД и файлы проверены. Прошу сверить gate,
но Timeweb пока не отключать до моего отдельного подтверждения.
```

Отдельное финальное подтверждение должно быть недвусмысленным:

```text
Подтверждаю отключение старого резервного копирования Timeweb после проверки
восстановления <дата>, snapshot <ID>. Подготовь PR удаления Compose backup.
Docker volumes не удаляй. Панель Timeweb отключу сам.
```

## 5. Включение MFA required

После optional rollout владелец сообщает:

```text
У меня и резервного security admin включены TOTP и сохранены recovery codes.
Проверки MFA/revoke/offboard прошли. Подтверждаю перевод политики в required.
Подготовь изменение и повторные auth tests, production включу отдельно.
```

Не включать required по одному предположению Claude.

## 6. Включение внешнего ИИ

```text
Прочитал data policy. Разрешаю внешнего provider <NAME> только для минимизированного
контекста после server-side фильтрации. Подготовь конфигурацию allow_minimized
без секретов и повтори canary/privacy tests. Пароли/ключи в диалог не передаю.
```

До такого сообщения provider остаётся `none`; help, tools и сводка должны работать.

## 7. Изменение требований

Любая новая просьба сначала классифицируется:

- **уточнение** — не меняет объём;
- **правка текущего этапа** — та же ветка/PR, повторить затронутые checks;
- **новый объём** — отдельная запись в журнале и оценка зависимостей;
- **production authorization** — явно отмечается отдельно, не выводится из общего «давай».

Шаблон:

```text
Новая правка: <…>.
Сначала остановись и оцени влияние на текущий этап, модель данных, права,
миграции и уже пройденные тесты. Не делай неявно production-изменений.
Если это новый объём, предложи отдельный этап.
```

Claude записывает в `15`: дата, старое решение, новое решение, причина, затронутые PR/tests. В `16` меняет статусы. Не переписывает историю как будто решение было всегда.

## 8. Замечания на review

```text
По PR #<N> есть замечания. Исправь в той же ветке, не создавай параллельный PR
для каждой правки. После исправления повтори связанные и общие regression checks,
обнови отчёт этапа и дай новый head commit.
```

Если main продвинулся:

```text
Актуализируй ветку относительно main без force-push и без отката чужих PR.
Разреши конфликты с сохранением новых бизнес-изменений, повтори миграционный
и функциональный набор.
```

## 9. Потеря контекста/новый диалог

Предпочтителен тот же диалог. Если он недоступен:

1. Передать актуальный ZIP/папку `docs/operations` из main.
2. Указать актуальный main commit и открытые PR.
3. Дать живые `15`, `16`, последние отчёты `17` и sanitized failing logs.
4. Не передавать production dumps, screenshots с данными или секреты.

Стартовое сообщение:

```text
Это продолжение внедрения. Сначала прочитай docs/operations, проверь фактический
main и открытые PR. Не полагайся на старый baseline, если он расходится.
Не повторяй уже слитые этапы. Покажи расхождения и продолжи с первого
незавершённого обязательного gate.
```

## 10. Запрещённые форматы работы

- «Перепиши весь проект заново» без отдельного решения.
- Новый репозиторий/standalone demo вместо текущего.
- Production dump «чтобы быстрее воспроизвести».
- Секрет в `.env.example`, prompt, screenshot или issue.
- «Тесты не запускал, но всё готово».
- Автоматический merge/deploy/migration/seed.
- Отключение Timeweb до restore.
- Добавление почты поддержки, потому что общий notify уже существует.
- Ослабление прав ради прохождения happy path.
- Скрытие failing/blocked checks и pre-existing issues.

## 11. Единый статус в ответе Claude

Каждый статус должен быть коротким и проверяемым:

```text
Main: <commit>, расхождения: <…>
Этап/ветка/PR: <…>
Сделано: <пути/функции>
Проверки: <фактические PASS/FAIL/BLOCKED и числа>
Миграции: rehearsal <…>, production НЕ применялись
Инфраструктура: <без изменений/что сделал владелец>
Проблемы: <…>
Дальше: <…>
Нужно владельцу: <точное действие без секретов>
```
