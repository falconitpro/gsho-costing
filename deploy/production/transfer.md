# Перенос данных со стенда на рабочий сервер

Решение владельца (D-058): со стенда переносится всё рабочее — сделки, заявки, каталоги, справочники, контрагенты, юридический блок, сотрудники, уровни доступа и личные исключения. Не переносятся пароли, коды из приложения, сессии и служебные данные стенда.

Способ: последняя копия стенда из Yandex Object Storage восстанавливается в пустую базу рабочего сервера и очищается одной командой. Это же — проверка восстановления.

Выполняется **между шагами 3 и 5** инструкции `install.md`, вместо шага 4. CRM на рабочем сервере в этот момент ещё не запущена.

## 1. Стенд: остановить работу и сделать копию

1. Предупредите сотрудников: с этого момента на стенд ничего не вносить. Всё, что внесут позже, на рабочий сервер не попадёт.
2. На стенде:

```bash
sudo systemctl start gsho-backup.service && sudo gsho-backup-status.sh --check
cd /opt/gsho-costing && docker compose exec backend python -m scripts.db_inventory > /root/stand-inventory.txt
```

Запишите ID снимка из вывода первой команды. Файл `stand-inventory.txt` — для сверки в шаге 4.

## 2. Рабочий сервер: ключ для чтения копий стенда

Нужны пароль копий стенда и ключ `sa-gsho-restore` (только чтение) — из защищённой заметки. Ключ записи копий стенда сюда не кладётся.

```bash
sudo apt-get install -y restic
sudo install -d -m 0700 /etc/gsho
sudo nano /etc/gsho/restore.env
sudo chmod 0600 /etc/gsho/restore.env
```

Содержимое `restore.env` — те же четыре строки, что на ВМ восстановления (`deploy/backup/recovery-smoke.md`, шаг 1): `RESTIC_REPOSITORY`, `RESTIC_PASSWORD`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, плюс `AWS_DEFAULT_REGION=ru-central1`.

## 3. Перенос

```bash
sudo bash /opt/gsho-costing/deploy/production/transfer-from-stand.sh --snapshot=<ID_СНИМКА>
```

Скрипт:
1. проверяет, что CRM не запущена и база пустая — иначе останавливается и ничего не меняет;
2. скачивает снимок и сверяет контрольные суммы; при несовпадении база не трогается;
3. восстанавливает базу и файлы;
4. доводит схему и применяет SQL `001…019`;
5. сбрасывает пароли, коды из приложения, сессии, уведомления, диалоги Помощника, пересмотр прав и журнал копий стенда;
6. заново загружает курсы ЦБ с cbr.ru;
7. печатает сводку по базе.

Что **не** меняется: сделки и заявки с расчётами и файлами, каталоги, справочники, контрагенты, договоры, доверенности, сотрудники с ролями, уровни доступа, личные исключения, журнал действий.

## 4. Сверка

Сравните сводку из шага 3 с `stand-inventory.txt`:
- число сделок, заявок, клиентов, заводов, запчастей, вложений — одинаковое;
- сотрудники те же, у всех в столбце «пароль» — `False`;
- `auth_sessions`, `mfa_credentials`, `notifications` в списке непустых таблиц отсутствуют.

Если что-то не сходится — CRM не запускать, прислать обе сводки.

## 5. Убрать ключ и копию стенда с рабочего сервера

Команда напечатана в конце шага 3:

```bash
sudo rm -f /etc/gsho/restore.env && sudo rm -rf /srv/gsho-transfer
```

## 6. Дальше

`install.md`, шаг 5: первый пользователь — ваша учётная запись ЗГД; команда выдаст временный пароль существующей записи, имя и роли не изменятся. Остальным сотрудникам пароли задаёте вы в «Настройки → Сотрудники»: каждый получает временный пароль и меняет его при входе.

После запуска:
- проверьте две-три сделки и вложения в них;
- демо-записи `@example.com` остались активными без паролей — войти под ними нельзя, пока вы не зададите пароль; замените в них адрес и имя на настоящие или отключите;
- загрузите курсы ещё раз, если шаг 3 сообщил «курсы не загружены»:
  `docker compose exec backend python -m scripts.prod_init fx`.

## Если перенос прервался

База при этом может быть заполнена частично. Вернуть пустую и повторить:

```bash
cd /opt/gsho-costing
docker compose -f docker-compose.yml -f docker-compose.prod.yml exec -T db psql -U gsho -d postgres -c "drop database gsho" -c "create database gsho"
```

Команда допустима только до первого запуска CRM на рабочем сервере. После запуска база удаляется только через восстановление из копии.
